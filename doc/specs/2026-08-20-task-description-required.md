# タスクに説明を必須で書かせる

日付: 2026-08-20
ゴール: 各タスクにタイトルだけでなく、何をやるタスクなのかの説明を必須で書くようにする

## 解く問題

`domain.Task` は説明を持たない。**実物を確認した結果:**

- `tasks` テーブルの列は 12 個（`id` `goal_id` `title` `status` `agent` `sort_order`
  `declare_key` `claimed_by` `claimed_at` `created_at` `updated_at` `files`）。
  `description` は無い
- `internal/domain/model.go:47-60` の `Task` にもフィールドが無い
- `atct_task_declare`（`internal/mcpshim/tools.go:17-18`）は `titles []string` と
  省略可の `files [][]string` だけを受け取る

そのため 2026-08-19 のゴール詳細の作業では、タスク詳細モーダルの「タスク説明」の位置に
**いま持っている属性**（触るファイル・担当・claim した run・日時）を出して代替した。
その報告の `needs_review` に「使ってみて足りないと分かったら説明フィールドを足す」と書き、
人間がこのゴールを立てた。

タイトルだけでは、**何をすれば終わりかが書かれていない。** 今日のこのプロジェクトでも
「承認が失敗したときに決定を open に巻き戻しているかを確かめる」というタスクを、
前提が誤っていたために取り下げている。前提と完了条件が書かれていれば、宣言した時点で
気づけた可能性がある。

## 決定

### 既存 241 件は埋めない（人間が 2026-08-20 に回答）

説明を必須にするのは**これから宣言するタスク**だけ。既存行は空のままにする。

理由: 既存タスクの説明を私が書くと、**私の推測がデータとして残り、実際の意図と区別できなくなる。**
2026-08-18 に同じことをやっている（完了報告の 6 項目を足したとき、未完了ゴール 15 件に
「なし」を書き込んだ）。

### DB は「空でないこと」を強制しない。宣言の経路で拒否する

**訂正（同日）: 当初ここに「`description` 列は NOT NULL にしない」と書いたのは誤り。**
`NOT NULL` と「空を禁止する」を混同していた。`NOT NULL DEFAULT ''` は空文字列を許すので、
この節の目的（DB に内容を強制させない）と矛盾しない。

列は `TEXT NOT NULL DEFAULT ''` にする。既存のスキーマが同じ形を採っている
（`agent TEXT NOT NULL DEFAULT ''`、`files TEXT NOT NULL DEFAULT '[]'`、
`claimed_by TEXT NOT NULL DEFAULT ''`）。既定値があるので既存 241 行は書き換わらず、
古いバイナリの INSERT も通り、Go 側に NULL の分岐が増えない。

空の拒否は `atct_task_declare` の経路で行う。**これは DB の制約より弱い。**
完了報告のときは `status='done'` という自然な切り分けがあったので CHECK を掛けられたが、
タスクにはそれに相当する条件が無い。「移行後に作られた行だけ」を CHECK で表すのは
`created_at` の比較になり壊れやすいので採らない。**弱いことを承知で Go 側に置く。**

### `descriptions` は `titles` と同じ長さの配列で受ける

`files` が既に `titles` と並行の配列なので、同じ形に揃える。長さが違えばエラー。
**`descriptions` は省略可にしない**（省略できるなら必須ではない）。

### 再宣言では説明を上書きしない

同じ `declare_key` での再宣言は既存行をそのまま残す（現在の冪等性の挙動を変えない）。
再宣言のたびに説明が書き換わると、**コンテキスト圧縮後の再試行が過去の記述を消す。**

### 画面では空のとき節ごと出さない

説明が空のタスクでは、モーダルの説明の節を描画しない。完了報告と同じ扱いで、
`product-ui` の空状態の指針にも揃う。**空の枠に「なし」と書いても何も伝わらない。**

### 説明に何を書くかを SKILL.md に書く

必須にするだけでは、タイトルの言い換えが 241 件増える。書くべきものを決める。

| 書くもの | 理由 |
|---|---|
| 終わったと判断する条件 | これが無いと、実装した本人以外は完了を判定できない |
| 前提にしていること | 誤っていれば宣言の時点で人間が正せる |

**タイトルは「何をするか」、説明は「終わりの条件」と「前提」。**
タイトルを言い換えただけの説明は、書いていないのと同じである。

## 検証

- 空の説明を含む `atct_task_declare` が**拒否されること**（否定側）
- `titles` と `descriptions` の長さが違う宣言が**拒否されること**（否定側）
- 既存 241 行が移行後も無変化であること（件数と `updated_at` を移行前と突き合わせる）
- 既存の空の説明のタスクで、モーダルの説明の節が**出ないこと**（否定側）
- 説明のあるタスクでは出ること
- 同じ `declare_key` で説明を変えて再宣言しても、**既存行が書き換わらないこと**（否定側）
- リリース済みの 1 つ前のバイナリで、移行後の DB が読めること

フィクスチャはタスク 2 件以上にする。1 件では「全行に同じ値を入れる実装」が通る。

実 HOME（`~/.atct`）の daemon は止めない。検証は一時 HOME と `VACUUM INTO` のコピーで行う。

## やらないこと

- 既存タスクの説明を埋めない（人間の回答）
- 説明の編集 UI を作らない（宣言するのはエージェントで、人間は却下で正す）
- `description` に長さの上限を DB で掛けるかは、完了報告の 2000 文字に揃えるかどうかを
  実装時に決める。**上限が無いと 1 タスクで画面が埋まる**ので、掛けない選択はしない
