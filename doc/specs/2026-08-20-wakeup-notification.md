# 取りこぼしを外から叩く

日付: 2026-08-20
発端: 人間の指摘「SSE は動いているわけだからサーバー側から定期的に wakeup 通知を送るのはどう？」

**状態: 未確定。実装しない**（人間の指示: 「wakeup の件は設計が固まるまで実装しないで」）。
以下は議論の記録であり、決定として扱わない。

## 解く問題

2026-08-20、commander が**やることが残っているのを知りながら、それを文章に書いてから止まった**
（「実装始めてよければ次に渡します」）。人間の CLAUDE.md・`/auto-run`・atct スキルの 3 つが
同じことを禁じている状況で起きた。

窓は 3 つある。

| 窓 | 仕組み | 状態 |
|---|---|---|
| ターンの最中 | SSE + Monitor | 動いている |
| ターンの終わり | Stop hook | 動いている |
| セッションが閉じている間 | cron + `atct context --check` | **対象外（下記）** |

**失速した瞬間、Stop hook は正しく発火した。何も報告しなかったのは、検知理由に
「宣言済みで未 claim のタスク」が無いからである。** 経路ではなく条件が足りていない。

### セッションが閉じている間は対象外（人間が 2026-08-20 に回答）

「セッションが閉じている」= Claude Code / Codex のプロセスが無い状態を指す。
Stop hook はターンが終わるときにしか発火せず、Monitor はセッションの中にしか存在せず、
`atct watch` はその Monitor の子プロセスである。**どちらも生きたセッションを前提とする。**

`atct context --check` はこの窓のために作られており、条件は
`cmd/atct/context.go:157-174` にあって**今日の失速の条件を既に含んでいる**
（168 行: `task.Status == todo && ClaimedBy == ""`）。しかし**それを起動する
cron / launchd の登録はこのマシンに存在しない**（実測: `crontab: no crontab`、
LaunchAgents に atct なし）。

人間の回答:「チャットが開いていない時をあらわしている場合、それは対応しなくてよい場合である」。

**この窓は埋めない。** `--check` はバイナリに残すが、スケジューラには登録しない。
結果として wakeup の設計は**生きたセッションだけを相手にし、
利用者のマシンの設定に一切触らない。**

## 決定

### 条件は列挙漏れを起こす。だから定期の起床を入れる

commander は当初「定期送信はコストが高いので避ける」と主張したが、**これは誤りだった。**
実測（1 回の起床あたり約 668 トークン、22 サンプル）で計算すると:

| 間隔 | 1 日あたり |
|---|---|
| 5 分 | 約 192k |
| 30 分 | 約 32k |
| 60 分 | 約 16k |

**30 分なら無視できる。** 5 分間隔の数字だけを出して間隔を選べることに触れなかったのが誤り。

より重要な点として、**条件による起動は誰かが思いついた失敗しか捕まえられない。**
今日の不具合そのものが「条件の列挙が不完全だった」ことなので、
**タイマーは条件が拾えないものを拾う。**

### 訂正: 評価の頻度と通知の頻度は分離できる。30 分待つ理由は無い

**上の表は「通知が毎回届く」前提の計算で、その前提が誤りだった**（人間の指摘:
「SSE への通知ってトークンコストないよね？」）。

コストの内訳は次のとおり。

| 経路 | トークン |
|---|---|
| daemon が評価する | 0 |
| SSE で publish・配送する | 0 |
| `atct watch` が stdout に 1 行出す | 0 |
| **その行が Monitor 経由でコンテキストに入る** | **約 668** |

**コストが出るのは最後の 1 ホップだけである。** つまり `atct watch` 側で
「やることが無ければ 1 行も出さない」と絞れば、**サーバは 30 秒ごとに評価してよく、
アイドル時のコストはゼロ、検知の遅れは 30 秒になる。**

30 分に落とす理由は無い。当初の「30 分から始める」は破棄する。

### トークンを使うのは「列挙漏れの保険」だけ

条件が 1 つも立っていなくても届く必要があるので、ここだけは必ずコストが出る。
低頻度（30〜60 分）に留め、**見えている状態を載せる**（下の節）。

**この部分の頻度と内容は未確定である。**

### 素の「確認しろ」にしない。見えている状態を載せる

**理由の無い起床は意志の失敗を直さない。** 今日の commander はやることがあるのを知って
文章に書いてから止まった。叩くだけでは同じ言い訳を繰り返す。

出すのは、いま見えているものの一覧である（アクティブなゴール数、タスク未 claim の件数、
回答待ちの件数）。**そうすれば条件の列挙が漏れていても、数字の食い違いに気づける。**
素の poke だと、条件が漏れていることは永久に分からない。

**やることが何も無いときは 1 行も出さない。** 22 回届いて 1 度も行動を変えなかった
心拍の行を作り直すことになる（慣れて効かなくなる）。

### SSE で押すか、watch が引くか（未決）

`internal/store/notify.go:20-23` の `DecisionEvent` は
`{Name string, Decision domain.Decision}` で、**決定を運ぶ形に固定されている。**
セッションの起床には決定が無い。

| 案 | 変更範囲 | コスト |
|---|---|---|
| SSE で押す | バスの一般化が必要（`notify.go` の型、`internal/httpapi/server.go:649` の購読、`cmd/atct/watch.go:425` の分岐、それぞれのテスト） | 0 |
| watch が 30 秒ごとに HTTP で引く | バスを触らない | 0 |

**コストはどちらも 0 で、遅れも同じである。** 違いは変更範囲と、watch が持つ仕組みの数。

押す案は watch の仕組みが 1 つ（SSE）で済む。引く案は SSE と polling の 2 つになるが、
型の変更が要らない。`watch.go:425` の switch は未知のイベント名を落とすので、
押す案でも古い watch は壊れない。

**どちらを採るかは未決。**

### 判定は 1 箇所に置き、3 経路から使う

`cmd/atct/pending.go` は DB を直接開いて判定している。SessionStart から呼ばれるため
**daemon の起動に依存できない**（`cmd/atct/context.go:34-36` のコメントに理由がある）。
一方 `atct watch` は HTTP で daemon と話す。

判定を `pending.go` に置いたままだと、watch から使うには DB を直接開く 2 本目の経路が増える。
**判定を store を受け取る関数として切り出し、`pending` と watch の両方から呼ぶ。**
同じ判定を 2 箇所に書かない（片方だけ直る事故を防ぐ）。

### 検知条件に「宣言済みで一度も claim されていないゴール」を足す

いまの 4 つの理由には無い。**足すが、収束する形で足す。**

「未 claim のタスクがある」は常に真になりうるので毎ターン継続を要求し、
打ち切り上限まで無駄になる（2026-08-18 にこの理由で意図的に外した。判断は正しい）。

収束する言い方は「**アクティブなゴールのうち、タスクが 1 件も claim されたことがないもの**」。
着手すれば消える有限のイベントで、既に採用されている「未分解のゴール」と同じ形である。

### 人間の回答待ちで止まっているものは条件から除く

答えられない仕事で永久に起こされる形にしない。

## 検証

- やることが無い状態で評価が何度も回っても、**1 行も出ないこと**（否定側。これが最重要）
- 宣言済みで未 claim のゴールがある状態で、**件数を含む行が出ること**
- **一度出したら、条件が変わるまで再送しないこと**（否定側）
- 条件が消えて再び真になったら、また出ること
- **他プロジェクトのゴールで起こされないこと**（否定側。2026-08-20 の
  `orphaned_decisions` の漏れと同じ形）
- 回答待ちで止まっているだけのゴールでは出ないこと（否定側）
- `atct pending` の既存 4 理由の出力が変わらないこと

フィクスチャはプロジェクト 2 件・ゴール 3 件以上にする。1 プロジェクトでは漏れを検出できない。

実 HOME（`~/.atct`）の daemon は止めない。

## 未決の論点

- SSE で押すか、watch が引くか
- 列挙漏れの保険の頻度と内容（ここだけトークンを使う）
- 評価の間隔（30 秒は daemon の既存タイマーに合わせた案。根拠は「既にそこにある」だけ）

## やらないこと

- 間隔を設定可能にする（固定で始める。動かしたくなってから足す）
- Stop hook の仕組みを変える（検知条件を足すだけ）
- **cron / launchd の登録**（セッションが閉じている窓は対象外と決めた）
