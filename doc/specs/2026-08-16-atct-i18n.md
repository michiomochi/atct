# ATCT Web UI Internationalization Design

Date: 2026-08-16
Status: approved
Supersedes: the "no i18n in v1, English only" decision recorded in
`doc/plans/2026-08-15-atct-plugin-distribution.md`

## 1. Problem

The Web UI ships English only. The user asked for Japanese as well.

A concrete symptom already exists: `GoalCreateForm.tsx:78` renders a Japanese sentence
because the implementation request spelled the example in Japanese. One string in one
language leaked into an English-only UI, and nothing in the codebase prevents the next one.

## 2. Scope

In scope:

- English and Japanese for every string the UI renders, including `aria-label`, `title`,
  and validation messages
- A language switch in the header
- Locale-aware date formatting
- A test that fails when a key exists in one language and not the other
- A measured before/after of `web/dist/` covering the new dependency

Out of scope:

- Any third language. The structure allows one to be added, but v1 ships two.
- Lazy-loaded locale bundles and HTTP backends for translations. Both locales are small
  enough to inline; a loader would add a request and a loading state for no benefit here.
- Translating data. Goal titles, questions, answers, `result_summary`, and project names
  are written by the user and by agents. They pass through untouched.
- Server-side messages. The HTTP API's `{"error": "..."}` strings stay English and are shown
  verbatim. **The UI does not pattern-match them to substitute translations**: that coupling
  breaks silently whenever the server rewords a message. What the UI does translate is its
  own framing around the raw message — the heading, the retry affordance, and the
  explanation of what failed.
- URL-based locales (`/ja/`, `/en/`).

## 3. Why not Astro's `astro:i18n`

`astro:i18n` provides locale routing and `Astro.currentLocale`. **It does not provide a
dictionary or a lookup function.**

ATCT renders almost every string inside React islands, so the locale would have to be passed
into React and resolved there against a dictionary — which is exactly what `react-i18next`
does. Adopting `astro:i18n` therefore adds routing on top of that work rather than replacing
it, and that routing is not free here:

- `/goals/{id}` currently falls back to `goals/_/index.html`. Locale prefixes turn that into
  two families and the daemon's fallback branch has to be rewritten. That branch has already
  produced two bugs.
- The static output doubles, and `web/dist/` is committed to git.

The usual payoff for locale routing is a shareable URL. ATCT serves `127.0.0.1`, so there is
no one to share it with.

## 3a. Library choice

**`react-i18next` is used.** This is the user's decision, recorded here so the reasoning
behind the code is not mistaken for an accident.

The alternative considered was a hand-written dictionary of roughly forty lines: a flat
record per locale, one interpolating lookup, and `Intl` for dates. At this size — two
screens, under a hundred strings, no plurals — that would have covered the requirement with
no new dependency.

The cost of the library is bundle size, and it lands somewhere that matters: `web/dist/` is
committed to git and already carries 552K after adopting Kumo. **The implementation measures
`web/dist/` before and after adding the dependency and reports both numbers**, so the trade
is visible rather than assumed.

What the library buys in return: a maintained interpolation and fallback implementation, a
familiar API for anyone who has used i18next elsewhere, and room to grow into namespaces,
plurals, and lazy-loaded locales without rewriting the call sites.

## 4. Dictionary

```
web/src/i18n/en.ts       English resources, the authoritative key set
web/src/i18n/ja.ts       Japanese resources
web/src/i18n/index.ts    i18next initialization, locale resolution, persistence
```

A single default namespace. Keys are dotted and grouped by screen area, for example
`inbox.openDecisions.title`. Dotted keys are configured as flat strings
(`keySeparator: false`) so the key set stays comparable between locales with a plain
`Object.keys` diff.

**English is authoritative.** `fallbackLng: "en"` means a key missing from Japanese renders
the English string. A blank label is worse than a label in the wrong language, and the
fallback keeps a partially translated build usable.

Interpolation uses i18next's `{{name}}` syntax. **`escapeValue` is disabled** because React
already escapes its output; leaving it on double-escapes apostrophes in the English strings.

No plural machinery is configured: counts render as bare numbers beside a heading, which
reads correctly in both languages.

## 5. Locale resolution

1. `localStorage["atct.locale"]` if it is `en` or `ja`
2. `navigator.language` starting with `ja` selects Japanese
3. English

The chosen locale is written back to `localStorage` on every switch. Nothing is stored
server-side; locale is a property of the browser, not of the account or the daemon.

## 6. Language switch

A control in the header, next to the existing Inbox link. Selecting a language re-renders
immediately from React state — no reload, no navigation, no URL change.

Both options are always visible and labelled in their own language (`English` / `日本語`),
so the switch is readable to someone who cannot read the current language.

## 7. Dates

All timestamps go through `Intl.DateTimeFormat` with the active locale. English keeps the
current `Aug 16, 2026, 6:48 PM` shape; Japanese renders `2026年8月16日 18:48`.

Elapsed claim durations (`42s`, `2h 15m`) are composed from translated unit strings rather
than hardcoded suffixes.

## 8. What must not regress

The existing UI decisions stay intact in both languages:

- Tables for Now and Next; the Needs decision column stays vertically stacked
- Two-line clamp with a `title` attribute in the inbox
- Counts beside each section heading
- Six screen states: empty, loading, error, validation, 409 conflict, data overload
- Horizontal scrolling confined to its container; the page body never scrolls sideways
- No emoji, no gradients, no nested cards, no promotional empty-state copy

Japanese text is denser than English at the same font size. Layouts must be verified in both
languages rather than assumed.

## 9. Testing

- **Key parity**: every key in `en.ts` exists in `ja.ts`, and the reverse. This is the test
  that would have caught the leaked Japanese sentence.
- Locale resolution across the three cases in section 5
- Interpolation
- Date formatting per locale
- Headless screenshots of the inbox and goal detail in both languages

## 10. Success criteria

1. Every rendered string, `aria-label`, and validation message changes with the switch.
2. No Japanese remains in the source outside `ja.ts`.
3. Switching does not reload the page or change the URL.
4. A key present in only one language fails the test suite.
5. Both languages render without layout breakage at the same viewport.
