# 委譲の作法を atct が持つ（多重化ツールに依存せずに）

2026-08-23。人間の指示: 「これを atct の skill 側につくりたい。herdr とかにべったり依存する
のではなく、ターミナルマルチプレクサ（tmux, herdr 等）を使っている場合はこう、使っていない
場合は sub-agent を使ってこうやる、とか atct 側にもってこれないかな？」
「そうじゃないと atct の本領が発揮できないため。すぐ commander がつまる」。

## なぜ atct が持つ必要があるか

**今日それが実際に起きた。**commander は 1 日で依頼書を 5 通書き、executor の圧縮を 8 回
起こし、レビュー中に `handler.go` の 825 行を消し、計測を 2 回間違えた。orchestration スキル
（dotfiles 側）は「commander は設計・実装・ファイルの編集をしない」と定めているが、
**その規則は atct を使う人の手元にあるとは限らない。**

atct のスキルは「claim してから着手しろ」「done にしろ」までは言うが、**その作業を誰が
どうやるかを一切言わない。**結果、1 つのセッションが全部を抱える形が既定になっている。

## 守ってきた制約: atct は多重化ツールを知らない

ゴール `44ae6e4e` で、claim を強制するフックを atct に置く案が却下されている。理由は
**「atct が herdr を知ることになる。公開物なので入れられない」。**

実測（2026-08-23）: この制約はいまも守られている。`herdr` / `tmux` への言及は
`internal/rpc/rpc.go` のコメント 1 行（先行事例として名前を出しているだけ）のみで、
コードにも設定にも依存が無い。

**この制約は正しい。**破らずに委譲の作法を入れる。

## 切り分け: 契約と検証は atct、機構は環境

```
atct が持つ      委譲する前に claim すること
                 働く側が自分の役割を名乗れること
                 名乗りが実態と合っているか検査できること（atct role）

環境が持つ        働く側をどうやって起こすか
                 役割をどうやって渡すか
```

**atct は「どうやって渡したか」を知る必要がない。**`atct role` が実態と突き合わせられれば、
渡し方は何でもよい。これが依存を切る要である。

## 2 つの形

スキルには**保証すべきこと**を書く。読む者は自分の環境がどちらかを即座に判断できる。

### ターミナルマルチプレクサを使っている場合

pane やウィンドウが独立した環境を持つ。コンテナや ssh 先も同じ形である。
**働く側の環境に環境変数を渡せる。**

```
1. タスクを claim する
2. 働く側の環境を作り、ATCT_ROLE=executor を渡す
3. 依頼の冒頭に「まず atct role を実行し、非 0 なら着手せず差し戻せ」と書く
```

### 使っていない場合（sub-agent）

働く側がこのセッションの中にいる。**独立した環境が無い。**

ここに罠がある。**sub-agent は親の環境を継ぐ。**commander が `ATCT_ROLE=commander` を
持っていれば、sub-agent もそれを見る。**黙って commander を名乗る。**

したがって sub-agent では**環境変数で渡せない。**引数で明示する。

```
1. タスクを claim する
2. sub-agent に役割を明示して起こす
3. 依頼の冒頭に「まず atct role --expect executor を実行し、非 0 なら着手せず差し戻せ」と書く
```

## 決定 1: `atct role` は期待値を引数でも受ける

```
atct role                      環境変数 ATCT_ROLE と実態を突き合わせる
atct role --expect executor    引数の期待値と実態を突き合わせる（環境変数より優先）
```

**sub-agent の場合に必要である。**環境変数しか見ないと、sub-agent は親の値を継いだまま
一致してしまい、検査が何も守らない。

実態は claim から導く（`session.role`、タスク `07f548e4`）。

```
プロジェクトの claim を持つ                → commander
ゴールの claim を持つ（プロジェクトは持たない）→ subcommander
どちらも持たない                          → executor
```

## 決定 2: 検証は働く側が自分で行う

**commander が渡して終わりにしない。**今日の pane 名がその失敗そのもので、
`atct-commander` と名乗ったまま 1 日中 subcommander の仕事をした。**名前は何も強制しない。**

依頼の冒頭で働く側が `atct role` を叩き、**非 0 なら着手せず差し戻す。**
これで「渡したつもり」と「受け取ったつもり」が分かれる。

## 決定 3: 一般名は書いてよい。個別ツールに依存しない

人間の判断（2026-08-23）: 「この制約はあるが、**ターミナルマルチプレクサという抽象的な
対象物であれば問題ない。**」

したがって次のように分ける。

```
書いてよい    「ターミナルマルチプレクサ」「sub-agent」といった一般名
              tmux のような、広く知られた標準的な例
書かない      herdr のような個別ツールの名前と、そのコマンドの綴り
```

**線は「読む者が自分の環境に読み替えられるか」である。**「ターミナルマルチプレクサを
使っているなら、pane を作るときに環境変数を渡せる」は誰でも読み替えられる。
`herdr pane split --env` は読み替えられないし、その綴りが変わると atct が壊れる。

**コマンドの綴りは書かない。**保証すべきことだけを書く。

```
ターミナルマルチプレクサを使っている  → 働く側の環境に ATCT_ROLE を渡せる
                                     渡し方はその道具の文書にある
使っていない                        → sub-agent を使う。環境変数は渡せないので
                                     atct role --expect <役割> で明示する
```

これで形 A / 形 B という抽象語を使わずに済み、読む者は自分がどちらかを即座に判断できる。

## 却下した案

**atct にフックを置いて claim を強制する** — `44ae6e4e` で却下済み。多重化ツールのコマンドを
見張ることになり、公開物に入れられない。**この spec は同じ穴を検査で塞ぐ**（`atct role` が
非 0 を返す）。強制ではなく検査だが、**強制は環境側に置ける**（dotfiles の
`claim-before-delegate.sh` が既にその形）。

**役割を新しい列で持つ** — `50b1fe60` で却下済み。claim から導く。

**commander の pane にも ATCT_ROLE を渡す** — 既に動いている環境には後から入れられない。
**claim からの導出に任せる。**

## 未検証

- **sub-agent が `atct` を叩けるか。**環境によっては bash が無い。無い場合、形 B では
  検査ができない。そのとき何を保証するかは決めていない
- **`atct role` が daemon を必要とするか。**`atct context` は DB を直接開くので daemon 不要
  だが、`session.role` は RPC である。**働く側が daemon に届かない環境**（別ホストの
  コンテナなど）では使えない。ターミナルマルチプレクサの一部の使い方で抜ける
- **両方が使える環境**でどちらを勧めるか。sub-agent のほうが軽いが、独立した環境が無いぶん
  取り違えやすい。決めていない
