# 委譲の作法を atct が持つ（多重化ツールに依存せずに）

2026-08-23。人間の指示: 「これを atct の skill 側につくりたい。herdr とかにべったり依存する
のではなく、ターミナルマルチプレクサ（tmux, herdr 等）を使っている場合はこう、使っていない
場合は sub-agent を使ってこうやる、とか atct 側にもってこれないかな？」
「そうじゃないと atct の本領が発揮できないため。すぐ commander がつまる」。

## なぜ atct が持つ必要があるか

**今日それが実際に起きた。**commander は 1 日で依頼書を 5 通書き、executor の圧縮を 8 回
起こし、レビュー中に `handler.go` の 825 行を消し、計測を 2 回間違えた。orchestration スキル
（dotfiles 側）は「commander は設計・実装・ファイルの編集をしない」と定めているが、
**その規則は atct を使う人の手元にあるとは限らない。**

atct のスキルは「claim してから着手しろ」「done にしろ」までは言うが、**その作業を誰が
どうやるかを一切言わない。**結果、1 つのセッションが全部を抱える形が既定になっている。

## 守ってきた制約: atct は多重化ツールを知らない

ゴール `44ae6e4e` で、claim を強制するフックを atct に置く案が却下されている。理由は
**「atct が herdr を知ることになる。公開物なので入れられない」。**

実測（2026-08-23）: この制約はいまも守られている。`herdr` / `tmux` への言及は
`internal/rpc/rpc.go` のコメント 1 行（先行事例として名前を出しているだけ）のみで、
コードにも設定にも依存が無い。

**この制約は正しい。**破らずに委譲の作法を入れる。

## 切り分け: 契約と検証は atct、機構は環境

```
atct が持つ      委譲する前に claim すること
                 働く側が自分の役割を名乗れること
                 名乗りが実態と合っているか検査できること（atct role）

環境が持つ        働く側をどうやって起こすか
                 役割をどうやって渡すか
```

**atct は「どうやって渡したか」を知る必要がない。**`atct role` が実態と突き合わせられれば、
渡し方は何でもよい。これが依存を切る要である。

## 決定 1: 環境変数は使わない。役割は必ず引数で渡す

人間の判断（2026-08-23）: 「であれば環境変数ではなく、すべて `--expect executor` とかで
渡すほうがよさそう」「**使い分けするのは負担が大きいので**」。**採る。**当初は
「環境変数を渡せるなら環境変数、渡せないなら引数」の二本立てにしていたが、一本にする。

### 理由 0: 使い分けそのものが負担である（人間の理由）

二本立てだと、委譲するたびに**まず自分の環境がどちらかを判断する**必要がある。
判断を間違えても静かに通る（環境変数を渡したつもりで渡っていない、など）。
**一本なら判断が要らない。**

以下の 3 つは commander が付け足した技術的な理由で、どれも同じ結論を支持する。

### 理由 1: 環境変数は構造的に嘘になる

役割は claim から導く。**claim はセッションの途中で変わる。**ゴールを claim した瞬間に
executor は subcommander になる。**pane を作るときに一度書いた環境変数は追随できない。**

結果、正しく働いているのに食い違いエラーが出るようになる。この spec の却下案
「commander の pane にも `ATCT_ROLE` を渡す」を入れられなかったのも同じ理由だった。
**片方だけ直しても、もう片方で同じことが起きる。**

### 理由 2: sub-agent は親の環境を継ぐ

commander が `ATCT_ROLE=commander` を持っていれば、sub-agent もそれを見る。
**黙って commander を名乗る。**環境変数しか見ない検査は、この場合何も守らない。

（この継承は一般のプロセス生成の性質から述べたもので、**実測はしていない。**
引数に一本化すればこの性質に依存しないので、確かめる必要も無くなる。）

### 理由 3: 環境変数があっても安全にならない

「環境変数なら、素の `atct role` でも検査が効く」と考えたが、**効かない。**
検査が走るのは依頼の冒頭でそのコマンドを実行したときだけで、実行しない相手は
引数の有無に関わらず実行しない。**環境変数は安全性を足していない。**

### したがって形は 1 つになる

```
1. タスクを claim する
2. 働く側を起こす（起こし方は環境の問題であり、atct は関知しない）
3. 依頼の冒頭に「まず atct role --expect <役割> を実行し、
   非 0 なら着手せず差し戻せ」と書く
```

**ターミナルマルチプレクサを使っていても、sub-agent を使っていても、同じ 1 行である。**
atct は環境を見分ける必要がなくなった。

### `--expect` を付けないとき

```
atct role                      いまの役割を報告する。検査はしない。exit 0
atct role --expect executor    期待値と実態を突き合わせる。食い違えば非 0
```

**報告と検査を分ける。**「自分は何者か」を知りたいだけの場面があるので、
引数なしを禁止にはしない。

実態は claim から導く（`session.role`、タスク `07f548e4`）。

```
プロジェクトの claim を持つ                → commander
ゴールの claim を持つ（プロジェクトは持たない）→ subcommander
どちらも持たない                          → executor
```

## 決定 2: 1 タスクに 1 人。差し戻しは同じタスクのうち

人間の指示（2026-08-23）: 「1 タスク毎に executor を建てるようにしたい」。

**同じ日の実測がこれを支持している。**

```
atct-executor    wakeup 実装 → 差し戻し → アダプタ削除 → 役割 2 件   圧縮 5 回
atct-executor-2  監査 → MCP 応答 → SKILL.md                        圧縮 2 回
```

積んだ数が多いほうが圧縮も多い。**圧縮のたびにスキルの再読が乗るので、圧縮が次の圧縮を
呼ぶ。**今日 1 台はこの循環に入り、2 ファイルの修正で 1 行も進まなくなって捨てた。

### 差し戻しは新しい人に渡さない

**ここを決めないと規則が使えない。**レビューで欠陥が見つかったとき、それは新しいタスクか。

**同じタスクである。**今日の A → B → A の修正は前の実装の差分で、新しい executor なら
`watch.go` と spec を読み直すことになる。**読み直しの費用は、積み上がりの費用より確実に
発生する。**

```
同じタスク（差し戻し・追加の質問・訂正）  → 同じ人に返す
別のタスク                              → 新しい人を立てる
```

**タスクが done になったら、その人は終わり。**次のタスクには新しい人を立てる。

### 使い回したくなる理由と、その反論

「新しい人は同じファイルを読み直すので、累計のコンテキストは増える」——**これは正しいが、
上限がある。**依頼書が読む対象を名指ししているので、読み直しはその集合で止まる。

**積み上がりには上限が無い。**タスクを積むほど履歴が伸び、読む対象を絞っても減らない。
今日 5 回圧縮した pane がそれである。

## 決定 3: 検証は働く側が自分で行う

**commander が渡して終わりにしない。**今日の pane 名がその失敗そのもので、
`atct-commander` と名乗ったまま 1 日中 subcommander の仕事をした。**名前は何も強制しない。**

依頼の冒頭で働く側が `atct role` を叩き、**非 0 なら着手せず差し戻す。**
これで「渡したつもり」と「受け取ったつもり」が分かれる。

## 決定 4: 一般名は書いてよい。個別ツールに依存しない

人間の判断（2026-08-23）: 「この制約はあるが、**ターミナルマルチプレクサという抽象的な
対象物であれば問題ない。**」

したがって次のように分ける。

```
書いてよい    「ターミナルマルチプレクサ」「sub-agent」といった一般名
              tmux のような、広く知られた標準的な例
書かない      herdr のような個別ツールの名前と、そのコマンドの綴り
```

**線は「読む者が自分の環境に読み替えられるか」である。**「ターミナルマルチプレクサを
使っているなら、pane を作るときに環境変数を渡せる」は誰でも読み替えられる。
`herdr pane split --env` は読み替えられないし、その綴りが変わると atct が壊れる。

**コマンドの綴りは書かない。**保証すべきことだけを書く。

```
ターミナルマルチプレクサを使っている  → pane を作って働く側を起こす
使っていない                        → sub-agent を起こす

どちらでも、依頼の冒頭は同じ 1 行:
    atct role --expect <役割> を実行し、非 0 なら着手せず差し戻せ
```

読む者は、自分がどちらの環境にいるかを即座に判断できる。

## 却下した案

**atct にフックを置いて claim を強制する** — `44ae6e4e` で却下済み。多重化ツールのコマンドを
見張ることになり、公開物に入れられない。**この spec は同じ穴を検査で塞ぐ**（`atct role` が
非 0 を返す）。強制ではなく検査だが、**強制は環境側に置ける**（dotfiles の
`claim-before-delegate.sh` が既にその形）。

**役割を新しい列で持つ** — `50b1fe60` で却下済み。claim から導く。

**環境変数 `ATCT_ROLE` で渡す** — 決定 1 で捨てた。役割は途中で変わるのに環境変数は
追随できず、sub-agent は親の値を継ぐ。**引数に一本化した。**

## 未検証

- **働く側が `atct` を叩けるか。**環境によっては bash が無い。無い場合、検査ができない。
  そのとき何を保証するかは決めていない
- **`atct role` が daemon を必要とするか。**`atct context` は DB を直接開くので daemon 不要
  だが、`session.role` は RPC である。**働く側が daemon に届かない環境**（別ホストの
  コンテナなど）では使えない。ターミナルマルチプレクサの一部の使い方で抜ける
- **両方が使える環境**でどちらを勧めるか。決定 1 で atct 側の扱いは同じになったので、
  選ぶ基準は環境の側にある。決めていない
