# claim が実行中かを事実で判定する

日付: 2026-08-20
発端: 人間の提案「claim と pid のマッピングを作るようにすればそのclaimが実行中なのかわかるんじゃない？」

## 解く問題

タスクの claim が「いま作業されているか」を判定する手段が無い。

実データにその症状が出ている（2026-08-20 実測）。

```
claimed_by = stock-data-5998ea32
claimed_at = 2026-08-18T17:12:13Z    （45 時間前）
runs テーブルに存在: 0 件
```

**45 時間前に着手されたまま放置され、その run は `runs` にもいない。**
どの検知経路にも出ない（`pending` は現在または最新の run の claim しか見ない）。

これは wakeup の設計（`2026-08-20-wakeup-notification.md`）の条件 5 と 7 が
どちらも「claim が生きているか」に依存するため、先に解く必要がある。

## 経過時間では判定できない

当初「`claimed_at` の経過時間で決める」案を出したが、**閾値の根拠が無い。**

`UpdateTaskStatusAndReleaseClaim` が `claimed_at = NULL` にするので、
**done になった 227 タスクすべてで claim の記録が消えている。** 保持時間を残す列も無い。
つまり「普通の claim はどれくらい続くのか」を過去のデータから測れない。

**さらに、複数のエージェントが同じプロジェクトで動くと誤判定する。**
「生きているがアイドル」（人間の入力を待っている）は commander の通常状態であり、
MCP の最終活動時刻ではそれを死亡と区別できない。誤って解放すると、
別の run が同じタスクを claim して**二重に作業する。**

## 決定

### 0. 後方互換性は判断材料にしない（人間が 2026-08-20 に回答）

「本プロダクトは自分しか利用者がいないので後方互換性とかは無視していい」。

**これで狭めていた選択肢が広がる。** 互換性を理由に採らなかったものが 3 つあった。

| 保留していたもの | 保留の理由（もう無効） |
|---|---|
| テーブルの改名 | 古い版の読み取りが壊れる |
| 通信の項目名の変更 | 古い MCP shim が壊れる（実際 0.8.0 と 0.12.0 が動いている） |
| `atlas` の baseline を v6 に据え置く | 古いバイナリが DB を読めなくなる |

**データの損失だけは別で、互換性とは無関係に守る**（実 DB を書き込みで開かない、
移行で内容を捏造しない）。

### 1. テーブルを `agent_sessions` に改名し、pid と起動時刻を足す

```sql
ALTER TABLE runs RENAME TO agent_sessions;
ALTER TABLE agent_sessions ADD COLUMN pid INTEGER NOT NULL DEFAULT 0;
ALTER TABLE agent_sessions ADD COLUMN started_at TEXT NOT NULL DEFAULT '';
```

**`runs` は「何の run か」を言えていない。** CI の語彙では run は「ジョブの 1 回の実行」で、
ここでの意味（エージェントのセッション 1 回）と重ならない。

`ai_sessions` も検討したが採らない。**スキーマに `ai` という語が 1 箇所も無く**（実測 0 箇所）、
このシステムは全体が AI 向けなので `ai_` は**システム全体を言い直しているだけ**である。

`agent_sessions` は既存の語彙につながる。`tasks.agent`（`schema.sql:50`）があり、
MCP の引数説明も "agent working directory" と書いている。**行為者は `agent` である。**
そして「1 つの agent が複数のセッションを持つ」関係が名前から読める（実際、今日
私は同じプロジェクトで複数の run ID を持った）。

### 1a. 識別子と通信の項目名も揃える

後方互換を気にしないので、**概念に 1 つの名前を与える。**

| 現在 | 変更後 | 箇所 |
|---|---|---|
| `runs` テーブル | `agent_sessions` | 16 |
| `decisions.run_id` | `agent_session_id` | 1 列 |
| `RunID` / `runID` | `AgentSessionID` / `agentSessionID` | 約 228 |
| `run_id`（JSON の項目名を含む） | `agent_session_id` | 79 |
| `RegisterRun` | `RegisterAgentSession` | 33 |
| `LatestRunID` | `LatestAgentSessionID` | 5 |
| `runRetention` | `agentSessionRetention` | 3 |

**`tasks.claimed_by` は改名しない。** 名前が既に意味を表しており、
中身が agent session の ID であることは spec に書けばよい。

**改名は挙動を変えないので、別の変更と混ぜない。** 壊れたときにどちらが原因か
分からなくなる。順序は「改名 + 列追加」→「判定の実装」とする。

**当初 `~/.atct/sessions/<pid>` というファイルの登録簿を提案したが、採らない。**
人間の指摘（「テーブル側で一元管理できないのかな？」）で根拠が 2 つとも崩れた。

**崩れた根拠 1: 「ファイルなら daemon と CLI の両方が読める」。**
`pending` も `store.Open(dbPath)` で DB を開く（`cmd/atct/pending.go:51`）。
テーブルも同じように読めるので、ファイルである利点になっていない。

**崩れた根拠 2: 「書き手を新しく作らずに済む」。** 逆だった。
**daemon がすでにこのテーブルへ書いている**（`internal/daemon/handler.go:101, 141` の
`RegisterRun`）。run が呼び出してきた時点で登録されるので、
**pid と起動時刻をその書き込みに足すだけでよい。** shim に「ファイルを作る・消す」という
新しい役割を足す必要がない。`~/.atct` に新しい規約も増えない。

保持期間（30 日、`internal/store/store.go:21`）の掃除もそのまま効く。

### 1b. 判定は daemon と CLI の両方から動く

`dir`（`~/.atct`、`cmd/atct/main.go:217`）配下の DB を見るので、2 つの読み手が同じものを見る。

| 読む側 | いつ | DB への到達方法 |
|---|---|---|
| daemon | 30 秒ごとの評価 | 常駐して開いている |
| `atct pending` | Stop hook から | **DB を直接開く**（daemon に依存できない） |

判定関数の形:

```
judge(store) → 実行中の claim / 放置された claim
```

**同じ判定を 2 箇所に書かない。** 今日、片方の経路だけ正しい状態を 2 回作っている
（`goal.tasks` と `decision_history.task_id`）。

### 2. shim は自分の pid と自分の起動時刻を送る

shim がリクエストに載せ、daemon が `RegisterRun` で刻む。
**自分のことなので、他プロセスを覗く必要がない。**

実測（2026-08-20）: MCP shim はセッションの直接の子である。

```
pid=32293  ppid=32242  atct-mcp-0.21.3
           ppid=32242 → claude
```

**セッションが死ねば shim も死ぬ**ので、shim の pid でセッションの生存を代表できる。

shim が再起動すると pid が変わり、生きているセッションの claim が
「実行されていない」と判定される。**その代償は通知 1 行であり、
自動解放をしないので作業は奪われない**（決定 6）。親の pid を取るために
他プロセスを覗くより、自分の値を送る方が確実である。

claim は MCP 経由でしか作られない（CLI に `claim` コマンドは無い）。
shim は `runID` を持っている（`internal/mcpshim/tools.go:147`）。

### 3. 起動時刻を併記する。pid の再利用が実害になる

**実測（2026-08-20）: PID は毎秒 60〜120 個消費されている。**

```
14:21:25  pid=69669
14:21:30  pid=70268   (+599)
14:21:35  pid=70562   (+294)
```

macOS の PID 空間は 99999 なので、**一周が約 15〜25 分。**
45 時間放置された claim の間に **約 135 周**している。

裏付け: 長寿プロセスの pid と起動時刻の順序が一致していない。

| pid | 起動 |
|---|---|
| 32242 | 8/19 01:02 |
| 94846 | 8/19 12:41 |
| 26357 | 8/20 12:32 |

pid だけで判定すると、**再利用された pid を「生きている」と誤判定し、
放置された claim が永久に抑制を掛け続ける** —— この設計が解こうとしている問題そのものになる。

`SIGKILL` で shim が落ちても `agent_sessions` の行は残る（行は履歴として残すのが正しい）ので、
**pid だけでは足りない。** 起動時刻まで一致しなければ別プロセスと判定する。

### 3b. OS に触る箇所が 1 つ残る

**「pid P の実際の起動時刻」は SQL では取れない。** 読み取り時に OS へ問い合わせる。
`ps -p <pid> -o lstart=` が macOS と Linux の両方で動き、依存関係を増やさない。
確認は 30 秒ごとに数件なのでコストは無視できる。

これを避ける方法を 2 つ検討して、両方だめだった。

| 案 | だめな理由 |
|---|---|
| shim の接続の切断で検知 | **shim は呼び出しごとに接続を張り直す**（`internal/mcpshim/client.go:35` の `defer conn.Close()`）。持続接続が無い |
| マシンの起動時刻と比較 | 再起動は検出できるが、**同一起動内の再利用（15〜25 分周期）を検出できない** |

**閾値ゼロを保つための代償として受け入れる。**

### 4. 判定は 3 段。閾値はゼロ

1. `claimed_by` の run ID が `agent_sessions` にあり、`pid` が 0 でないか
2. その pid が生きているか
3. `agent_sessions.started_at` が、その pid の実際の起動時刻と一致するか

3 つすべて満たせば **実行中**。1 つでも欠ければ **実行されていない**。

**推測が 1 つも入らない。** 「35 時間」も「30 分」も要らない。

### 5. 判定できないときは「実行されていない」とみなす

登録簿が読めない、起動時刻が取れないなどで判定できない場合は、
**実行されていない側に倒す** = 通知が出る。

理由: 見逃し（通知が出ない）が、この一連の作業で直そうとしている失敗である。
余分な通知 1 行のコストは、見逃しより安い。

**なお 2026-08-19 の「担当プロジェクト以外への書き込みを拒否する」では逆に倒した**
（判定できないときは通す）。あちらは**拒否すると正常な操作が落ちる**ためで、
こちらは**倒しても 1 行増えるだけ**なので、向きが違うのは意図的である。

### 6. 自動で解放しない。報告だけする

判定が正確になっても、claim を自動で解放しない。

**放置された claim の害は「通知を抑制すること」だけであり、
その claim について通知が出た時点で害は消えている。** 解放はエージェントが文脈を見て
判断し、必要なら人間に聞く。

**二重に作業する経路を作らないため。** 判定が正しくても、解放を自動にすると
「判定のバグ 1 つで他のセッションの作業を奪う」形になる。

## これで解ける wakeup の条件

| 条件 | 解き方 |
|---|---|
| 3. claim したまま閉じていない | 既存（Stop hook） |
| 5. 宣言済みだが着手されていない | **実行中の claim が無く、未着手のタスクがある** |
| 7. 死んだ run の claim が残っている | **登録簿で実行中でない run が claim を持っている** |
| 通知の抑制（作業中なら送らない） | **実行中の claim がある** |

同じプロジェクトで何台動いていても、**それぞれの pid が別なので誤判定しない。**

## 検証

- `agent_sessions` に pid と起動時刻があり pid も生きて起動時刻が一致 → **実行中**
- **否定側**: pid が生きているが**起動時刻が違う** → 実行されていない
  （pid 再利用の検出。実際に pid を再利用させて測る）
- **否定側**: 行はあるが pid が死んでいる → 実行されていない
- **否定側**: `pid = 0` の古い行（改名直後の既存 8 行）→ 実行されていない
- **否定側**: 他プロジェクトの run の claim で、こちらのプロジェクトの通知が
  抑制されないこと（プロジェクト 2 件で測る）
- shim が終了するとファイルが消えること
- **shim を `SIGKILL` した後、ファイルが残ったままでも「実行されていない」と
  判定されること**（起動時刻の突き合わせが効いていることの確認）
- 実データのコピーで、45 時間放置された claim が「実行されていない」と判定されること

実 HOME（`~/.atct`）の daemon は止めない。**検証は一時 HOME で行う。**

## やらないこと

- claim の自動解放（決定 6）
- `claimed_at` の経過時間による判定（根拠が無い）
- 心拍列の追加（pid と起動時刻で足りる。定期書き込みを増やさない）
- ファイルの登録簿（`~/.atct/sessions/`）を作ること。テーブルで足りる
- 別のマシンで動く run の判定（ATCT は unix socket と 127.0.0.1 のローカル前提）

## 記録: 別の穴

`UpdateTaskStatus`（`internal/store/queries/task.sql:27`）は `WHERE id = ?` だけで
`claimed_by` を見ていない。**どの run でも他人のタスクを done にできる。**
claim が守っているのは claim 自体だけで、作業は守っていない。

この作業の範囲外だが、claim の意味を弱めているので記録しておく。
**後方互換を気にしないので、直すことに障害は無い。** 別のゴールとして立てる。
