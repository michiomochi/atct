# claim が実行中かを事実で判定する

日付: 2026-08-20
発端: 人間の提案「claim と pid のマッピングを作るようにすればそのclaimが実行中なのかわかるんじゃない？」

## 解く問題

タスクの claim が「いま作業されているか」を判定する手段が無い。

実データにその症状が出ている（2026-08-20 実測）。

```
claimed_by = stock-data-5998ea32
claimed_at = 2026-08-18T17:12:13Z    （45 時間前）
runs テーブルに存在: 0 件
```

**45 時間前に着手されたまま放置され、その run は `runs` にもいない。**
どの検知経路にも出ない（`pending` は現在または最新の run の claim しか見ない）。

これは wakeup の設計（`2026-08-20-wakeup-notification.md`）の条件 5 と 7 が
どちらも「claim が生きているか」に依存するため、先に解く必要がある。

## 経過時間では判定できない

当初「`claimed_at` の経過時間で決める」案を出したが、**閾値の根拠が無い。**

`UpdateTaskStatusAndReleaseClaim` が `claimed_at = NULL` にするので、
**done になった 227 タスクすべてで claim の記録が消えている。** 保持時間を残す列も無い。
つまり「普通の claim はどれくらい続くのか」を過去のデータから測れない。

**さらに、複数のエージェントが同じプロジェクトで動くと誤判定する。**
「生きているがアイドル」（人間の入力を待っている）は commander の通常状態であり、
MCP の最終活動時刻ではそれを死亡と区別できない。誤って解放すると、
別の run が同じタスクを claim して**二重に作業する。**

## 決定

### 1. run ID と pid の登録簿を持つ。名前は `sessions`

```
~/.atct/sessions/<pid>   →  <run ID> <プロセスの起動時刻>
```

**`runs` にしない。** `runs` は既にテーブル名（`id` / `project_id` / `registered_at`）であり、
別物と区別できない。記録しているのは shim の親、つまり**セッションのプロセス**なので
意味としても `sessions` が正確である。

MCP shim が起動時に書き、終了時に消す。**タスクに列を足さない**
（`claimed_by` に run ID が既に入っている）。

先例は `~/.atct/watchers/<pid>`（`internal/daemonctl/stop.go:16` の `RegisterWatch`）。
`filepath.Join(dir, "watchers")` に `os.Getpid()` の名前でファイルを作り、
クリーンアップ関数を返す形をそのまま使う。

```
~/.atct/
  atct.db
  atct.sock
  watchers/<pid>    ← SSE を購読しているプロセス（既存）
  sessions/<pid>    ← run ID を持つセッション（新規）
```

### 1b. 判定はファイルなので daemon と CLI の両方から読める

これが要点である。`dir`（`~/.atct`、`cmd/atct/main.go:217`）の下に置くので、
**2 つの読み手が同じものを見られる。**

| 読む側 | いつ | DB への到達方法 |
|---|---|---|
| daemon | 30 秒ごとの評価 | 常駐して開いている |
| `atct pending` | Stop hook から | **DB を直接開く**（daemon に依存できない） |

`pending` は `pendingTextForProject(dir, cwd, ...)` で既に `dir` を受け取っている
（`cmd/atct/pending.go:50-51`）。同じ `dir` から登録簿も読める。

判定関数の形:

```
judge(store, dir) → 実行中の claim / 放置された claim
```

`store` と `dir` を渡せば、daemon 経由でも DB 直読みでも同じ判定が動く。
**同じ判定を 2 箇所に書かない。**

### 2. 記録するのは shim の pid ではなく、その親（セッション）の pid

実測（2026-08-20）: MCP shim はセッションの直接の子である。

```
pid=32293  ppid=32242  atct-mcp-0.21.3
           ppid=32242 → claude
```

**セッションが死ねば shim も死ぬ。** ただし shim が何かの理由で再起動すると
shim の pid は変わるので、**親の pid を記録する**。そうすれば shim の再起動をまたいで
同じ値になる。

claim は MCP 経由でしか作られない（CLI に `claim` コマンドは無い）。
shim は `runID` を持っている（`internal/mcpshim/tools.go:147`）。

### 3. 起動時刻を併記する。pid の再利用が実害になる

**実測（2026-08-20）: PID は毎秒 60〜120 個消費されている。**

```
14:21:25  pid=69669
14:21:30  pid=70268   (+599)
14:21:35  pid=70562   (+294)
```

macOS の PID 空間は 99999 なので、**一周が約 15〜25 分。**
45 時間放置された claim の間に **約 135 周**している。

裏付け: 長寿プロセスの pid と起動時刻の順序が一致していない。

| pid | 起動 |
|---|---|
| 32242 | 8/19 01:02 |
| 94846 | 8/19 12:41 |
| 26357 | 8/20 12:32 |

pid だけで判定すると、**再利用された pid を「生きている」と誤判定し、
放置された claim が永久に抑制を掛け続ける** —— この設計が解こうとしている問題そのものになる。

`SIGKILL` で shim が落ちると登録簿のファイルが残るので、**中身の run ID だけでは足りない。**
起動時刻まで一致しなければ別プロセスと判定する（`ps -p <pid> -o lstart=` と突き合わせる）。

### 4. 判定は 4 段。閾値はゼロ

1. `claimed_by` の run ID に対応する登録簿のファイルがあるか
2. その pid が生きているか
3. ファイルの run ID が `claimed_by` と一致するか
4. ファイルの起動時刻が、その pid の実際の起動時刻と一致するか

すべて満たせば **実行中**。1 つでも欠ければ **実行されていない**。

**推測が 1 つも入らない。** 「35 時間」も「30 分」も要らない。

### 5. 判定できないときは「実行されていない」とみなす

登録簿が読めない、起動時刻が取れないなどで判定できない場合は、
**実行されていない側に倒す** = 通知が出る。

理由: 見逃し（通知が出ない）が、この一連の作業で直そうとしている失敗である。
余分な通知 1 行のコストは、見逃しより安い。

**なお 2026-08-19 の「担当プロジェクト以外への書き込みを拒否する」では逆に倒した**
（判定できないときは通す）。あちらは**拒否すると正常な操作が落ちる**ためで、
こちらは**倒しても 1 行増えるだけ**なので、向きが違うのは意図的である。

### 6. 自動で解放しない。報告だけする

判定が正確になっても、claim を自動で解放しない。

**放置された claim の害は「通知を抑制すること」だけであり、
その claim について通知が出た時点で害は消えている。** 解放はエージェントが文脈を見て
判断し、必要なら人間に聞く。

**二重に作業する経路を作らないため。** 判定が正しくても、解放を自動にすると
「判定のバグ 1 つで他のセッションの作業を奪う」形になる。

## これで解ける wakeup の条件

| 条件 | 解き方 |
|---|---|
| 3. claim したまま閉じていない | 既存（Stop hook） |
| 5. 宣言済みだが着手されていない | **実行中の claim が無く、未着手のタスクがある** |
| 7. 死んだ run の claim が残っている | **登録簿で実行中でない run が claim を持っている** |
| 通知の抑制（作業中なら送らない） | **実行中の claim がある** |

同じプロジェクトで何台動いていても、**それぞれの pid が別なので誤判定しない。**

## 検証

- 登録簿のファイルがあり pid も生きていて run ID と起動時刻が一致 → **実行中**
- **否定側**: pid が生きているが**起動時刻が違う** → 実行されていない
  （pid 再利用の検出。実際に pid を再利用させて測る）
- **否定側**: ファイルはあるが pid が死んでいる → 実行されていない
- **否定側**: ファイルが無い（`SIGKILL` 後に手で消した状態）→ 実行されていない
- **否定側**: 他プロジェクトの run の claim で、こちらのプロジェクトの通知が
  抑制されないこと（プロジェクト 2 件で測る）
- shim が終了するとファイルが消えること
- **shim を `SIGKILL` した後、ファイルが残ったままでも「実行されていない」と
  判定されること**（起動時刻の突き合わせが効いていることの確認）
- 実データのコピーで、45 時間放置された claim が「実行されていない」と判定されること

実 HOME（`~/.atct`）の daemon は止めない。**登録簿の検証は一時 HOME で行う。**

## やらないこと

- claim の自動解放（決定 6）
- `claimed_at` の経過時間による判定（根拠が無い）
- `runs` テーブルへの心拍列の追加（登録簿で足りる。定期書き込みを増やさない）
- 登録簿を `runs` という名前にすること（テーブル名と衝突する）
- 別のマシンで動く run の判定（ATCT は unix socket と 127.0.0.1 のローカル前提）

## 記録: 別の穴

`UpdateTaskStatus`（`internal/store/queries/task.sql:27`）は `WHERE id = ?` だけで
`claimed_by` を見ていない。**どの run でも他人のタスクを done にできる。**
claim が守っているのは claim 自体だけで、作業は守っていない。

この作業の範囲外だが、claim の意味を弱めているので記録しておく。
