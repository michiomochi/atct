# 回答が届いた瞬間にエージェントへ push する

日付: 2026-08-19
ゴール: 回答が AI エージェントに確実に届くようにする（承認却下を受けての追加）

## 解く問題

回答から適用までの遅れが実データに残っている（1 分 16 秒、3 分）。どちらもエージェントが
長い作業の途中だった時間である。今ある経路はどちらもその区間を埋められない。

- Stop hook: ターンが**終わったとき**に発火する。作業中は届かない
- 全 MCP ツールのレスポンスに添付: 次にツールを呼ぶまで待つ

## 決定

### Monitor で daemon の SSE を張る

daemon はすでに `/api/events` で SSE を配信している（`event: <名前>` と
`data: <decision の JSON>`、決定の状態遷移ごとに publish）。Claude Code の `Monitor`
ツールは長時間コマンドの stdout を 1 行 1 通知に変える。これを繋ぐ。

**実測（2026-08-19 10:29:07）**: 75 秒後に 1 行出すだけの Monitor を張ってセッションを
アイドルにしたところ、**イベントだけでターンが起きた**。人間の入力は無い。
`Monitor` は作業中とアイドルの両方をカバーする。

### cron・`/loop`・`ScheduleWakeup` は使わない

どれも「ターンの合間」にしか発火しない。`CronCreate` は REPL が idle のときだけで、
7 日で失効し、セッションのメモリ上にしか無い。ターンの合間は Stop hook がすでに
押さえているので、足しても埋まる区間が増えない。加えて発火ごとに 1 ターン消費するのに対し、
Monitor は回答が来るまでトークンを使わない。

**cron が勝つのは「購読できるものが無く、状態を問い合わせるしかない」場合である。**
ATCT は SSE を持っているので該当しない。

### `atct watch` を作る（`curl` を直に張らせない）

Monitor に渡すコマンドは `atct watch` にする。理由は 3 つある。

- daemon のポートは既定 8787 だが、埋まっていれば 8788・8789 に落ちる。解決を
  エージェントに書かせない
- daemon の再起動で SSE が切れる。**再接続は `atct watch` が持つ**。切れたまま黙るのが
  最悪の壊れ方である（通知が来ないことは「回答が無い」と区別できない）
- 出力の形を固定できる。1 行 1 イベント、人間が読める短い文、`decision_id` を含む

出すのは**人間が答えた遷移だけ**に絞る。エージェント自身の `decision_ask` や `poll` で
起きた遷移まで出すと、自分の操作で自分が起きる。

### 張るのはセッションの最初

`atct:start` skill と SKILL.md に「最初に `atct watch` を Monitor で張れ」と書く。
**仕組みがあっても指示が無ければ張られない。** Stop hook は実装から実運用まで
「あるのに効いていない」状態が 1 度あった（run_id が起動ごとに変わっていた）。

### ハーネスによる書き分け

`Monitor` は Claude Code の機能で、Codex には無い。SSE 経路は Claude Code の主経路、
MCP レスポンスへの添付は全ハーネス共通の土台として残す。**片方に寄せて他方を消さない。**

### 対象外

セッションが 1 つも動いていない間は埋めない（2026-08-19 の回答）。Monitor も cron も
Claude Code のプロセスが生きている前提である。

## 検証

- `atct watch` が SSE を購読し、人間が回答した瞬間に 1 行出すこと
- daemon を再起動しても購読が復帰すること（切れたまま黙らないこと）
- エージェント自身の操作で起きた遷移では出さないこと
- 実測: セッションをアイドルにして人間が回答し、ターンが起きて回答が適用されること。
  遅れを秒で記録する（比較対象は既存の 1 分 16 秒と 3 分）

実 HOME（`~/.atct`）では検証しない。一時 HOME と専用ポートを使う。
