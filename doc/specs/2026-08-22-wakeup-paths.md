# wakeup の経路設計と、いま動いていないところ

2026-08-22。人間の指摘「定期的な wakeup 通知が機能していないように思う。例えば今だと
goal c3e0fae0 はまだ進行できるが、あなたは止まったままである」から書き起こした。

この文書は**いまのコードから読み取った事実**と、**そこから説明できる不具合**を分ける。
事実には出どころ（ファイルと関数）を付けた。推測には推測と書いた。

## 事実

### 発火の間隔と回数

| 事実 | 出どころ |
|---|---|
| 保守処理は 30 秒ごと | `internal/daemon/server.go` の `time.NewTicker(30 * time.Second)` |
| `keepalive` は毎回出る | `runMaintenance` が無条件に `PublishEvent` |
| `wakeup` の条件は `ActiveGoalCount > 0 && UnstartedTaskCount > 0` | `internal/daemon/wakeup.go` |
| 条件成立から **15 分**待って初めて出す | 同 `wakeupPublishAfter = 15 * time.Minute` |
| 出したら `published[project] = true` で**二度目を出さない** | 同 |
| 条件が偽になると `activeSince` と `published` を**削除**（時計が 0 に戻る） | 同 |
| `detection.*` も同じ 15 分と、条件ごとの重複排除 | 同 `publishDetection` |

**つまり `wakeup` は定期通知ではない。**「条件が 15 分続いたら 1 回」であり、条件が
途切れるたびに時計が 0 に戻る。

### 未着手の数え方

`UnstartedTaskCount` は `DetectWakeup`（`internal/store/wakeup.go`）が返す。ゴールを 1 つずつ
見て、**次の 2 つのどちらかに当たるゴールは `continue` で丸ごと飛ばす。**

```go
if len(openDecisions) > 0 {          // ① open な決定が 1 件でもある
    state.WaitingAnswerCount += len(openDecisions)
    continue
}
if _, ok := runningByGoal[goal.ID]; ok {   // ② 生存中の claim が 1 件でもある
    continue
}
// ここまで来たゴールだけ、todo かつ未 claim を数える
```

どちらも**ゴール単位**である。タスク単位ではない。
出どころのコミットは `f10d947` "Poke the agent when work is sitting untouched, **and stay
silent otherwise**" で、**黙っていることが設計意図**だったと読める。

### いまの実データ（2026-08-22 の指摘を受けた直後に測った）

active なゴールのうち「todo かつ未 claim のタスクを持つもの」を分類した。

| 区分 | ゴール数 |
|---|---|
| 未着手を持つ active ゴール | 8 |
| └ ① open な決定があって飛ばされる | 3 |
| └ ② 生存中の claim があって飛ばされる | 2 |
| └ 数に残る | 3 |

```
未着手タスク合計        10
数に数えられた未着手      5   ← 半分が消えている
```

**したがって、いま `ActiveGoalCount = 3`・`UnstartedTaskCount = 5` で、`active` の条件は
成立している。**条件が成立していないから鳴らないのではない。

## 説明できる不具合

### (1) 一度出したら二度と出ない（これが人間の指摘の直接の原因）

```go
} else if !t.published[project.ID] && !now.Before(startedAt.Add(wakeupPublishAfter)) {
        events = append(events, ...)   // wakeup を出す
        t.published[project.ID] = true // ← 以後この project では出ない
}
```

`t.published` が下りるのは、**条件が偽になったときだけ**（`!active` の枝で
`delete(t.published, project.ID)`）。

いま条件は成立している（上の実データ）。**つまり `published` は立ったままで、
この project ではもう `wakeup` が出ない。**

**「何もなくても定期的に送られるはず」という期待に対して、定期的に送る仕組みは
存在しない。**「条件が 15 分続いたら 1 回、条件が切れるまで沈黙」である。
未着手が常に 1 件は残っている実運用では、**実質「1 回だけ」**になる。

### (2) 忙しいときは 15 分に届かない

条件が偽に振れると `activeSince` も消えるので、時計が 0 に戻る。claim・close・宣言を
数分おきにやっている間は、15 分の連続を満たしにくい。(1) と組み合わさると
「鳴るのは、しばらく暇になってから作業を再開した直後の 1 回だけ」になる。

### (3) 除外がゴール単位なので、半分が数から消える

上の実データで **10 件のうち 5 件**が消えていた。内訳は ① で 3 ゴール、② で 2 ゴール。

- **① open な決定があるゴールを飛ばす**のは、「人間の回答を待っている間は急かさない」と
  読める。だが**完了報告の承認待ちが典型で、いま 17 の active ゴールが該当する。**
  承認待ちのゴールに未着手タスクが残っていても、永久に数に出ない
- **② 生存中の claim があるゴールを飛ばす**のは、「もう手が付いている」と読める。だが
  commander は claim を先に取る規則で常に claim を持っているので、**作業中のゴールの
  残りタスクが見えない**

人間が挙げた例は ② である。指摘を受けた時点の `c3e0fae0` は:

```
6a789bcc  done   ゴールに派生元を保存できるようにする
9f0af794  todo   CLAIMED   ← commander が claim 済み（executor に渡していない）
b912c5c0  todo   -         ← 未着手・未 claim。これが「まだ進行できる」の実体
```

`c3e0fae0` に open な決定は無い（実測）ので、効いているのは ② で確定。
**`9f0af794` の claim 1 件が、同じゴールの `b912c5c0` を数から消していた。**

### (4) claim したまま何もしない状態を、どちらの経路も検知しない

検知条件に `detection.unclaimed_doing`（claim 無しで doing）はあるが、**その逆
（claim 済みで何も起きていない）は無い。**2026-08-22 に commander は `9f0af794` を
claim したまま約 1 時間半、executor に渡さず放置した。この間:

- `wakeup` は (1) と (3)② の両方の理由で鳴らない
- `detection.*` はどの条件にも当たらない
- Stop hook は「作業ロックを持っている」と表示するが、**それは正常な状態と同じ表示**

### (5) Stop hook は「止まった」しか知らない

`plugin/hooks/stop` は `atct pending` の出力が空でなければブロックする。
**実際に commander を動かしてきたのはこの経路だけである。**ただしこの経路は
「ターンを終えようとした」ことしか検知できない。**散文を返し続ければ、ブロックは
繰り返されるが、行動を強制する力はない。**今日 3 回、「これから投げます」と書いて
投げずにターンを終えた。そのたびに Stop hook はブロックしたが、次のターンでも同じことが
起きた。

## 直す候補（commander の提案）

### F. `wakeup` を、条件が続いている間は繰り返し出す

**(1) の直接の原因で、人間の指摘そのもの。**`published` を真偽の掛け金ではなく
「最後に出した時刻」にして、一定間隔で再送する。

- 得るもの: **「何もなくても定期的に送られる」という期待どおりになる**
- 代償: 間隔を決める必要がある。短いと通知が邪魔になる（`f10d947` の "stay silent
  otherwise" と衝突する）
- 併せて: (2) も同時に軽くなる。条件が一時的に偽に振れても、次の周期で拾える

### G. ゴール単位の除外をタスク単位にする

**(3) の直接の原因。**① と ② のどちらも、**そのゴールの他のタスクまで巻き込んでいる。**

- ①: 決定に紐づいているタスクだけを除外する（`decisions.task_id` がある）
- ②: claim されているタスクだけを除外する
- 得るもの: 実測で消えていた 5 件が数に出る。人間の挙げた例が検知される
- 代償: 通知が増える。`f10d947` の意図（黙っている）と正面から衝突するので、
  **F の間隔と合わせて決める必要がある**
- 注意: `CountUnstartedTasksForWakeup`（commit 4d085b3 で検知側にそろえた比較用の
  数え方）も同じ規則に直さないと、`wakeup.discrepancy` が誤検知に戻る

### H. 「claim したまま進んでいない」を検知条件に足す

(4) の直接の原因。

- 代償: 「何も起きていない」の定義が要る。commander が claim して executor に渡した後、
  タスク自体には数十分何も起きない（コミットも status の変化も無い）のが正常なので、
  **単純な時間切れでは正常な委譲を叩く**
- 推測: 作業ロックの取得時刻と、そのゴールのコミットの有無を組み合わせれば分けられる。
  **未検証**

### I. Stop hook に「前回と同じ pending を 2 回続けて出したか」を持たせる

(5) の直接の原因。同じ内容でブロックが繰り返されているなら、**それは行動していない
合図である。**2 回目以降は文面を変えて、行動を名指しする。

- 得るもの: 「これから投げます」と書いて終わる形が止まる
- 代償: 状態を持つ必要がある（前回の pending の内容をどこかに残す）
- 推測: `~/.atct` に前回の pending のハッシュを置けば足りる。**未検証**

## commander の推奨

**F → G の順に 1 つのゴールでやる。H と I は別のゴールに分ける。**

F と G は同じ緊張関係（どれだけ鳴らすか）の裏表なので、**別々に決めると必ず片方が
もう片方を打ち消す。**F だけ入れると、除外で半分消えた数を定期的に鳴らすだけになる。
G だけ入れると、数は正しくなるが 1 回しか鳴らない。

H は「正常な委譲」と「放置」を分ける定義が未検証。I は atct ではなくこの環境の設定に
近いが、`plugin/hooks/stop` は atct の公開物なので atct 側で持てる。

**この文書に書いた「未検証」は、確かめる前に実装してはいけない。**2026-08-21 に
同じ形で 3 回外している。この文書自身も一度外した（当初 (3) の例に claim 済みの
`9f0af794` を「未着手」と書き、実データを見て `b912c5c0` に直した）。
