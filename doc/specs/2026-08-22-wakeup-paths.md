# wakeup の経路設計と、いま動いていないところ

2026-08-22。人間の指摘「定期的な wakeup 通知が機能していないように思う。例えば今だと
goal goal 73 はまだ進行できるが、あなたは止まったままである」から書き起こした。

この文書は**いまのコードから読み取った事実**と、**そこから説明できる不具合**を分ける。
事実には出どころ（ファイルと関数）を付けた。推測には推測と書いた。

## 事実

### 発火の間隔と回数

| 事実 | 出どころ |
|---|---|
| 保守処理は 30 秒ごと | `internal/daemon/server.go` の `time.NewTicker(30 * time.Second)` |
| `keepalive` は毎回出る | `runMaintenance` が無条件に `PublishEvent` |
| `wakeup` の条件は `ActiveGoalCount > 0 && UnstartedTaskCount > 0` | `internal/daemon/wakeup.go` |
| 条件成立から **15 分**待って初めて出す | 同 `wakeupPublishAfter = 15 * time.Minute` |
| 出したら `published[project] = true` で**二度目を出さない** | 同 |
| 条件が偽になると `activeSince` と `published` を**削除**（時計が 0 に戻る） | 同 |
| `detection.*` も同じ 15 分と、条件ごとの重複排除 | 同 `publishDetection` |

**つまり `wakeup` は定期通知ではない。**「条件が 15 分続いたら 1 回」であり、条件が
途切れるたびに時計が 0 に戻る。

### 未着手の数え方

`UnstartedTaskCount` は `DetectWakeup`（`internal/store/wakeup.go`）が返す。ゴールを 1 つずつ
見て、**次の 2 つのどちらかに当たるゴールは `continue` で丸ごと飛ばす。**

```go
if len(openDecisions) > 0 {          // ① open な決定が 1 件でもある
    state.WaitingAnswerCount += len(openDecisions)
    continue
}
if _, ok := runningByGoal[goal.ID]; ok {   // ② 生存中の claim が 1 件でもある
    continue
}
// ここまで来たゴールだけ、todo かつ未 claim を数える
```

どちらも**ゴール単位**である。タスク単位ではない。
出どころのコミットは `f10d947` "Poke the agent when work is sitting untouched, **and stay
silent otherwise**" で、**黙っていることが設計意図**だったと読める。

### watch 側は繰り返しを止めない

`cmd/atct/watch.go` は重複排除を持つが、`wakeup` の鍵は **`eventName + wakeupID`** である。

```go
type watchWakeupDeliveryKey struct {
	eventName string
	wakeupID  string
}
```

`wakeupID` は publish のたびに `store.NewWakeupID()` で新しく作られる
（`internal/daemon/wakeup.go`）。**したがって同じ条件で何度出しても watch は捨てず、
1 行ずつ Monitor に流れる。**繰り返し通知するために watch を変える必要はない。

（`detection.*` は逆で、鍵が対象 ID なので意図的に 1 回に絞られている。
`watch.go` のコメントがそう書いている。）

### いまの実データ（2026-08-22 の指摘を受けた直後に測った）

active なゴールのうち「todo かつ未 claim のタスクを持つもの」を分類した。

| 区分 | ゴール数 |
|---|---|
| 未着手を持つ active ゴール | 8 |
| └ ① open な決定があって飛ばされる | 3 |
| └ ② 生存中の claim があって飛ばされる | 2 |
| └ 数に残る | 3 |

```
未着手タスク合計        10
数に数えられた未着手      5   ← 半分が消えている
```

**したがって、いま `ActiveGoalCount = 3`・`UnstartedTaskCount = 5` で、`active` の条件は
成立している。**条件が成立していないから鳴らないのではない。

### 実装後の実測（2026-08-22・稼働版 0.38.0）

決めた値（初回 10 分・再送 10 分）を入れて、SSE を 25 分の窓で 1 行ずつ時刻付きで記録した。

```
10:53:10  wakeup（4 プロジェクト分が同時に届く）
11:03:40  wakeup（atct 分）
差:       10 分 30 秒
```

**設計どおりである。**保守処理は 30 秒周期なので、10 分を過ぎた**次の tick**で送る。
実効間隔は「10 分を 30 秒単位で切り上げ」になる。初回も daemon 起動（10:44 前後）の
約 10 分後で整合している。

**時計が戻っていないことも確認した。**keepalive が 11:02:10 / 11:02:40 / 11:03:10 /
11:03:40 と連続しており、tick は途切れていない。2 回目が 11:03:10 ではなく 11:03:40 に
なったのは、`now` と `lastPublishedAt + 10 分` の比較がミリ秒単位で前者を下回り、
1 tick 分ずれたためである。

**このとき見つかった欠陥 2 件は (6) と (7) に書いた。**

## 説明できる不具合

### (1) 一度出したら二度と出ない（これが人間の指摘の直接の原因）

```go
} else if !t.published[project.ID] && !now.Before(startedAt.Add(wakeupPublishAfter)) {
        events = append(events, ...)   // wakeup を出す
        t.published[project.ID] = true // ← 以後この project では出ない
}
```

`t.published` が下りるのは、**条件が偽になったときだけ**（`!active` の枝で
`delete(t.published, project.ID)`）。

いま条件は成立している（上の実データ）。**つまり `published` は立ったままで、
この project ではもう `wakeup` が出ない。**

**「何もなくても定期的に送られるはず」という期待に対して、定期的に送る仕組みは
存在しない。**「条件が 15 分続いたら 1 回、条件が切れるまで沈黙」である。
未着手が常に 1 件は残っている実運用では、**実質「1 回だけ」**になる。

### (2) 忙しいときは 15 分に届かない

条件が偽に振れると `activeSince` も消えるので、時計が 0 に戻る。claim・close・宣言を
数分おきにやっている間は、15 分の連続を満たしにくい。(1) と組み合わさると
「鳴るのは、しばらく暇になってから作業を再開した直後の 1 回だけ」になる。

### (3) 除外がゴール単位なので、半分が数から消える

上の実データで **10 件のうち 5 件**が消えていた。内訳は ① で 3 ゴール、② で 2 ゴール。

- **① open な決定があるゴールを飛ばす**のは、「人間の回答を待っている間は急かさない」と
  読める。だが**完了報告の承認待ちが典型で、いま 17 の active ゴールが該当する。**
  承認待ちのゴールに未着手タスクが残っていても、永久に数に出ない
- **② 生存中の claim があるゴールを飛ばす**のは、「もう手が付いている」と読める。だが
  commander は claim を先に取る規則で常に claim を持っているので、**作業中のゴールの
  残りタスクが見えない**

人間が挙げた例は ② である。指摘を受けた時点の `goal 73` は:

```
task 413  done   ゴールに派生元を保存できるようにする
task 414  todo   CLAIMED   ← commander が claim 済み（executor に渡していない）
task 415  todo   -         ← 未着手・未 claim。これが「まだ進行できる」の実体
```

`goal 73` に open な決定は無い（実測）ので、効いているのは ② で確定。
**`task 414` の claim 1 件が、同じゴールの `task 415` を数から消していた。**

### (4) claim したまま何もしない状態を、どちらの経路も検知しない

検知条件に `detection.unclaimed_doing`（claim 無しで doing）はあるが、**その逆
（claim 済みで何も起きていない）は無い。**2026-08-22 に commander は `task 414` を
claim したまま約 1 時間半、executor に渡さず放置した。この間:

- `wakeup` は (1) と (3)② の両方の理由で鳴らない
- `detection.*` はどの条件にも当たらない
- Stop hook は「作業ロックを持っている」と表示するが、**それは正常な状態と同じ表示**

### (5) Stop hook は「止まった」しか知らない

`plugin/hooks/stop` は `atct pending` の出力が空でなければブロックする。
**実際に commander を動かしてきたのはこの経路だけである。**ただしこの経路は
「ターンを終えようとした」ことしか検知できない。**散文を返し続ければ、ブロックは
繰り返されるが、行動を強制する力はない。**今日 3 回、「これから投げます」と書いて
投げずにターンを終えた。そのたびに Stop hook はブロックしたが、次のターンでも同じことが
起きた。

### (6) 合計と一覧が食い違う（4fa3330 と c52eea8 の組み合わせで生じた）

**どちらの変更も単独では正しい。**全件数える（4fa3330）と、繰り返し送る（c52eea8）。
だが `state.Tasks`（急かす一覧）に入るのは「open な決定が無く、かつ生存中 claim も
無いゴール」のタスクだけだったため、**数には出るのに一覧では隠れたまま**になった。

稼働版 0.38.0 で実測した状態:

```
goal 73:  task 414 todo CLAIMED   ← commander が持っている
           task 415 todo FREE      ← claim できるのに一覧に出ない
           task 444 todo FREE      ← 同じ

atct pending の出力: "You hold 3 work locks." だけ。未着手の行が 0 件
0.37.0 では task 415 が出ていた ── 後退
```

**これは人間が最初に指摘した不具合そのものである。**原因は「作業中」という分類が
**タスク単位では意味を持たない**こと。未着手かつ未 claim なら定義上 claim できる。
「作業中」は同じゴールの別タスクが動いている事情でしかない。

直した（28b68da）。回答待ちは `decisions.task_id` を使ってタスク単位にした。

### (7) 内訳がイベントに乗っていない（依頼を 3 つに割った継ぎ目）

`store.WakeupState` に内訳を足し（4fa3330）、`cmd/atct/watch.go` が内訳を印字する
ようにした（4637f65）。だが **`store.WakeupEvent` には内訳のフィールドが無かった。**

稼働版に届いた実際の 1 行:

```
atct wakeup: active_goals=2 unstarted_tasks=2 waiting_answer_tasks=0 working_tasks=0 untouched_tasks=0 waiting_answers=11
```

**合計 2 に対して内訳が 0/0/0。**JSON にキーが無く、Go のゼロ値が印字されていた。

原因は commander の依頼の割り方である。3 つに割ったときに、**イベントの受け渡しを
誰の担当にも書かなかった。**各 executor は自分の担当を果たしていた。

直した（b2c1d95）。`unstarted_task_count = waiting_answer_task_count +
untouched_task_count` をイベントの側で検査している。

## 決まった設計（2026-08-22・人間の判断）

候補として F〜I を並べていたが、人間から 2 つの決定が出た。**どちらも当初の案より
踏み込んでいる。**

### 決定 1: 条件がクリアになるまで通知し続ける

> 「1 回だけでなく、条件がクリアになるまでずっと通知するのはどう？」

`published` を真偽の掛け金ではなくし、**条件が成立している間は繰り返し出す。**

- **watch 側の変更は不要**（上記「watch 側は繰り返しを止めない」）。daemon 側 1 か所
- `f10d947` の "stay silent otherwise" と正面から衝突する。**意図を変える決定である**

#### 間隔を実行ログから決める

当初 commander は「保守処理の周期（30 秒）ごとに出す」と書いた。**実測したら使えない数
だった。**

atct プロジェクトの 708 件のイベント（`tasks` と `goals` と `decisions` の書き込み、
2026-08-17〜2026-08-22 の 4.4 日）から、**エージェントの操作の間隔**を出した。

| p50 | p75 | p90 | p95 | p99 | 最大 |
|---|---|---|---|---|---|
| 0.6 分 | 3.7 分 | 13.8 分 | 24.5 分 | 225 分 | 496 分 |

**いまの 15 分はほぼ p90 に一致する**（15 分を超える間隔が 66/707 = 9.3%）。恣意的な数
ではなかった。

そのうえで、初回待ちと再送間隔の組で通知数を試算した。

| 初回待ち | 再送間隔 | 4.4 日の総通知数 | 鳴った間隔の数 | 90 分停滞での通知数 |
|---|---|---|---|---|
| 15 分 | 30 秒 | 8,501 | 66 | 151 |
| 5 分 | 30 秒 | 10,439 | 139 | 171 |
| 3 分 | 5 分 | 1,218 | 198 | 18 |
| 10 分 | 10 分 | 510 | 89 | 9 |
| 15 分 | 15 分 | 323 | 66 | 6 |

**支配的なのは再送間隔で、初回待ちの効きは小さい。**30 秒で鳴らし続けると 1 日あたり
約 2,000 件、90 分の停滞 1 回で 151 件になる。

**決めた値: 初回 10 分・再送 10 分。**

- 10 分は p75（3.7 分）と p90（13.8 分）の間にあり、707 件の間隔のうち鳴るのは 89 件
  （12.6%）。**異常な間だけ鳴る**
- 90 分の停滞で 9 回鳴る。無視できない一方で埋もれない
- 4.4 日で 510 件（1 日約 116 件）。active ゴール 26 件・未着手 10 件という現在の
  滞留量での数なので、片付くにつれ減る

**この試算は atct 1 プロジェクト分である。**測ったのは atct プロジェクトの書き込みの
間隔だが、**`wakeup` はプロジェクト単位で出る。**

**実測（2026-08-22 10:53:10、稼働版 0.38.0）**: 1 回の周期で 3 行が同時に届いた。

```
10:53:10  project 1ff70f35 (atct)  active_goal_count=2 unstarted_task_count=2
10:53:10  project 07f68b94         active_goal_count=1 unstarted_task_count=1
10:53:10  project bb5b1775         active_goal_count=1 unstarted_task_count=1
```

したがって**通知の総数は、条件を満たすプロジェクトの数だけ倍になる。**上の試算表の値は
atct 分だけであり、実際はそれより多い。**間隔を決め直すときは、プロジェクト数を掛けた
数で見ること。**

もう 1 つ、試算は上限でもある。測ったのは「何らかの書き込みの間隔」で、wakeup の条件
（未着手があり作業ロックが無い）が成立している時間はその部分集合である。この 2 つは
逆向きに働くので、**実数を測り直すまでどちらに転ぶかは分からない。**

### 決定 2: 未着手は全件とってから判断する

> 「未着手は全件とって判断すべきでは？」

当初の案（G）は除外をゴール単位からタスク単位に細かくするものだったが、**数える段階で
情報を捨てる形は変えていなかった。**決定はそこを変える。

```
いま      : 数えながら捨てる     → 「未着手 5」（何を捨てたか分からない）
これから  : 全件とってから分ける → 「未着手 10、うち回答待ち 3、作業中 2、手つかず 5」
```

- **`f10d947` の「黙っている」意図は、表示の選択として残せる。**いまはデータを消して
  いるので選択の余地が無い。数えることと判断することを分ける
- `WakeupState` に「除外された理由つきの内訳」が乗る形になる
- `CountUnstartedTasksForWakeup`（commit 4d085b3 で検知側にそろえた比較用の数え方）も
  同じ規則に直す。直さないと `wakeup.discrepancy` が誤検知に戻る
- watch の 1 行と `atct pending` の文面が変わる。内訳を出すなら両方を直す

## 残っている候補

### H. 「claim したまま進んでいない」を検知条件に足す

(4) の直接の原因。**人間からより良い設計が出たので、この案は取り下げる。**

> 「claim 依頼と claim 受領を管理するテーブルを作成し、それぞれ依頼をするのは
> commander、受領をするのは executor の役割とする。そのテーブルで依頼はしているが
> 受領はしていない、または受領はしているが依頼はしていないことを監視する monitor を
> 作成し、commander がそれを監視する。」

H は「何も起きていない」を時間で測るもので、**委譲後のタスクには数十分何も起きないのが
正常**なため、単純な時間切れでは正常な委譲を叩く。定義が未検証で詰まっていた。
受領を明示的に記録させれば、**時間ではなく構造で判定できる。**

実測した前提（2026-08-22）:

- **「依頼」側は新規に作る必要がない。**`atct_task_claim` が既に依頼の記録である
- **「受領」側は書けない。**Codex に atct の MCP は入っておらず（`~/.codex/config.toml`
  に記載が無い）、CLI の書き込み系は `project add` と `goal add` だけ
  （`claim-check` は読み取り専用）
- したがって **executor が受領を書く経路を新しく作るのが最初の決めどころ**

未検証: 依頼から受領までの猶予。秒単位で済むはずだが、executor が前の作業中なら遅れる。
0 では誤検知する。

この件はゴール `goal 85` として切り出した。

### I. Stop hook に「前回と同じ pending を 2 回続けて出したか」を持たせる

(5) の直接の原因。同じ内容でブロックが繰り返されているなら、**それは行動していない
合図である。**2 回目以降は文面を変えて、行動を名指しする。

- 代償: 状態を持つ必要がある（前回の pending の内容をどこかに残す）
- 推測: `~/.atct` に前回の pending のハッシュを置けば足りる。**未検証**

## working_tasks が常に 0 になった経緯（2026-08-22 に追跡）

この文書の上のほうに「合計 2 に対して内訳が 0/0/0」という実測がある。あれは
**JSON にキーが無く Go のゼロ値が印字されていた**欠陥で、`b2c1d95` で直った。

**しかし `working_tasks` だけは直っていなかった。**別の理由で 0 だったのが、

## WAL が本体より大きくなるのは、直す理由にならない（2026-08-22 に実測）

### 切り分け

一時 daemon（空の DB）に 400 件の書き込みを入れて WAL を 4.12MB まで膨らませ、
**同じデータ・同じ payload（129,355 バイト）**で、チェックポイントの前後を測った。

WAL         0 バイト   50.2 / 49.7 / 43.8 / 41.5 / 38.7 ms

**差が無い。**WAL のサイズは読みの応答時間に効かない。SQLite の WAL は索引で引くので、

### これは設計の穴ではない。前提の食い違いである

`completion_report_missing` は「作業が終わったのに報告を忘れている」を捕まえる検知で、
**その前提は「タスクが全部 done ならゴールは達成している」である。**

今日はその前提が崩れた。**5 件とも全タスク done で、ゴールは未達だった。**
分けたタスクの境界に落ちたもの（呼ぶ経路）が、どのタスクの完了条件にも入っていなかった。

### 当面どうするか

**再提出しない。**達成していないゴールの完了報告を出すのは、内容の誤りである。
催促は鳴るが、**鳴っている理由が正しく「このゴールは終わっていない」なので、
黙らせるべきではない。**

解けるのは、切り出したゴール（`goal 103` / `goal 104` / `goal 105`）が承認され、
親ゴールに新しいタスクを宣言できるようになったときである。

### 検知の側を直すなら

「全タスク done」ではなく「全タスク done かつ**却下された完了報告が無い**」に絞れば、
この往復は消える。**ただし今日はまだ提案しない。**1 日の観測で検知の条件を変えるのは
早い。**同じ形が別の日にも起きるかを見てからにする。**

## 見送りが要る具体例が出た（2026-08-22・自分で作ってしまった）

未達のゴール 5 件に「何を待っているか」をタスクとして宣言した。**5 件とも未承認の
ゴール待ちで、着手できない。**それでも催促は「着手できるタスクが 5 件ある」と言う。

```
task 492  handoff の経路ができたあと、4 通りを実測する          → goal 104 待ち
task 493  handoff の経路ができたあと、3 つの止まり方を実測する   → goal 104 待ち
task 494  見送りの経路ができたあと、催促が止まることを実測する    → goal 105 待ち
task 491  セッションの追い出しが直ったあと、2 人目が拒まれる…    → goal 103 待ち
task 495  役割ごとの上限が入ったあと、3 層を実際に立てて実測する  → goal 103 待ち
```

**催促は「未着手」しか見ない。**「誰も拾っていないから未着手」と「ブロックされているから
未着手」を区別しない。区別する仕組みが `snoozed_until` であり、**その書く経路が無い**
（`goal 105`）。

**つまり `goal 105` が入るまで、この 5 件は鳴り続ける。**そして `task 494` は
その `goal 105` を待っているタスクなので、**自分が解決する問題に自分が当たっている。**

### claim して黙らせない

claim は「いま作業している」の意味である。着手できないタスクを claim すると、
**ダッシュボードが嘘になる。**今日 `goal 42` が防ごうとしたのは逆向き（委譲したのに
claim しない）だが、**claim の意味を曲げる点では同じ害である。**

鳴らせたままにする。**鳴っている理由は正しい**——このタスクは未着手で、
着手できない理由は人間の承認待ちだからである。
