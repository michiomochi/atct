# ゴールの本文を直せるようにする

2026-08-22。ゴール `141d71dc`「ゴールの本文を作成後に直せないので、前提が古くなった
まま承認を待たせてしまう」の中の判断。

## 起きたこと

commander がゴール `44433505` を立て、本文に「dotfiles のフックが `herdr agent start`
を見て止める」と書いた。**その後 2 回訂正が入った。**

```
1 回目  agent start には cwd の指定が無い     → pane split を見る
2 回目  subcommander は pane ではなく space   → workspace create を見る
```

**spec は 2 回とも直したが、ゴールの本文は直せなかった。**人間が承認の画面で読むのは
本文なので、**古い前提のまま判断を求めることになった。**

## 判断: 履歴は「承認時の本文」だけ残す

候補は 3 つあった。

| 案 | 得るもの | 代償 |
|---|---|---|
| (1) 別テーブルに履歴を積む | 全部の変更が追える | テーブルが増える。**読む人がいない履歴が溜まる** |
| (2) 追記だけを許す | 実装が単純 | **今回の用途（誤りを直す）に使えない** |
| **(3) 承認時の本文を決定に保存** | **「何を承認したか」が承認と一緒に残る** | 承認前の変更は追えない |

**(3) を採る。**

### なぜ

**危ないのは「承認したものと違うものが実行される」ことである。**それを防ぐには
**承認の瞬間の本文**があれば足りる。編集の全履歴は要らない。

そして `goal_approval` の決定は**ゴールごとに 1 件**で、`question` は
`"Approve this goal?"` の固定文である（実測）。**本文は入っていない。**
ここに本文を入れれば、**新しいテーブルが要らない。**

### 承認前の変更を追えないことについて

**それは害ではない。**承認前の本文は「提案の下書き」であり、**人間がまだ何も約束して
いない段階**である。下書きの変遷を残しても読む人がいない。

**承認後の変更は追える。**承認済みのゴールの本文を直すと、決定に保存された本文と
食い違う。**その食い違いこそが見たいものである。**

## 実装の注意

- **完了報告の 6 フィールド（`work_done` ほか）は `goals` テーブルに同居している。**
  本文を更新する経路が、それらを巻き込まないこと
- `goals` を作り直す移行（`0007`）が既にある。**列を足すなら `ALTER TABLE ADD COLUMN`
  にして作り直さない**（作り直すと外部キーの問題に当たる。`1980f14` が接続単位で
  `foreign_keys` を切る処理を入れている）
- **承認済みのゴールの本文を直せるかは別の判断。**この spec は「直せるようにする」ことと
  「承認時の本文を残す」ことだけを決めている
