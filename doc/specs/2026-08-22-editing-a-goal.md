# ゴールの本文を直せるようにする

2026-08-22。ゴール `141d71dc`「ゴールの本文を作成後に直せないので、前提が古くなった
まま承認を待たせてしまう」の中の判断。

## 起きたこと

commander がゴール `44433505` を立て、本文に「dotfiles のフックが `herdr agent start`
を見て止める」と書いた。**その後 2 回訂正が入った。**

```
1 回目  agent start には cwd の指定が無い     → pane split を見る
2 回目  subcommander は pane ではなく space   → workspace create を見る
```

**spec は 2 回とも直したが、ゴールの本文は直せなかった。**人間が承認の画面で読むのは
本文なので、**古い前提のまま判断を求めることになった。**

## 判断: 提案中だけ書き換えられるようにする。履歴は持たない

**人間の判断（2026-08-22）**:

> であれば承認後は本文変更できないけど提案中のものは変更できるだけでいいんじゃない？

```
提案中  → 書き換えられる（承認前なので、人間はまだ何も約束していない）
承認後  → 書き換えられない（承認したものが動く）
```

**これで履歴の問題そのものが消える。**

### commander の案は却下された

commander は「書き換えられるようにして、承認時の本文を決定に保存する」と提案した。
**人間はより単純な形を選んだ。**

**書き換えられる範囲を絞れば、守る仕組みが要らない。**「書き換えられるようにして履歴で
守る」は、**足す方向の解**だった。

そして**今日の実際の困り方に十分である。**`44433505` の本文を直したかったのは
**提案中の間**だった（承認を待たせている最中に前提が 2 回変わった）。

### 却下された案（記録）

| 案 | なぜ却下されたか |
|---|---|
| 別テーブルに履歴を積む | テーブルが増える。読む人がいない履歴が溜まる |
| 追記だけを許す | 誤りを直す用途に使えない |
| 承認時の本文を決定に保存 | **仕組みを足さずに済む形があった** |

## 実装の注意

- **完了報告の 6 フィールド（`work_done` ほか）は `goals` テーブルに同居している。**
  本文を更新する経路が、それらを巻き込まないこと
- `goals` を作り直す移行（`0007`）が既にある。**列を足すなら `ALTER TABLE ADD COLUMN`
  にして作り直さない**（作り直すと外部キーの問題に当たる。`1980f14` が接続単位で
  `foreign_keys` を切る処理を入れている）
- **承認済みのゴールは拒む。**`status` を見て、`proposed` 以外なら拒否する。
  エラーは `errors.Is` で区別できる形にする
- **履歴は持たない。**別テーブルも決定への保存も要らない

## 完了条件のうち 1 つは稼働版では測れない（2026-08-22 に実測）

タスク `e89d0d00`「稼働版で書き換えを実測する」の記録。完了条件は
「稼働版で実際に書き換えて、**履歴が残ること**と**完了報告が壊れないこと**を両方測る」。

**両方とも、書かれた時点の前提が変わっている。**

### 「履歴が残ること」は消えた

このタスクは履歴を持つ案を前提に書かれた。**その後人間が「提案中だけ書き換えられる」を
選び、履歴は作らないことになった**（この文書の上のほうの判断）。
`c5a369c4`（履歴のゴール）も却下済み。**残る履歴は無いので、測る対象が無い。**

### 「完了報告が壊れないこと」は原理的に測れない

**提案中のゴールは完了報告を持てない。**実測（一時 daemon・0.41.0）:

```
新しい提案中のゴールを作る                → status=proposed
そのまま goal.complete を投げる           → "goal has an open decision"
```

提案中のゴールは**必ず承認の決定を持つ**（`ErrGoalHasOpenDecision`、
`internal/store/decision.go:21`）。したがって完了報告を書けない。
本番の提案中 8 件を見ても、完了報告の 7 フィールドは全部 0 文字である。

**「提案中」と「完了報告あり」は同時に存在しない。**書き換えられるのは提案中だけなので、
**壊れうる完了報告がそもそも無い。**

この不変条件はテストのフィクスチャでしか作れない
（`TestUpdateGoalContentPreservesCompletionReport` が 6 フィールドに値を入れてから
書き換える形で作っている）。**それでよい。**列が同居している以上、
`UPDATE goals SET content = ?, work_done = ''` のような書き間違いは起こりうるので、
検査自体には意味がある。**測る場所がテストだというだけである。**

### したがって稼働版で測るのはこの 3 つ

```
1. 提案中のゴールの本文が実際に書き換わる
2. active / done / dropped が拒まれる
3. 書き換えたあと完了報告の 7 フィールドが空のままである（自明だが確かめる）
```

測る対象として `44433505` が理想的である。**提案中のまま本文に古い記述が残っている**
（24 行目「dotfiles のフック herdr agent start を見て…」）。
これはこのゴールを立てる原因になった、2 回訂正が入った箇所そのものである。

## リリース前に全経路を通した（2026-08-22 に実測）

main（`91845ba`）からビルドしたバイナリを一時 daemon に載せ、空でない実データの上で
8 項目を測った。**リリース後の確認を短くするため、先にここで通しておく。**

### daemon / MCP の経路

```
1. 提案中の本文を goal.update_content で書き換える  → 成功。複数行もそのまま入る
2. 読み直して実際に変わっている                     → 変わっている
3. 完了報告の 7 フィールドが空のまま                 → 7 つとも 0 文字
4. active に投げる                                 → "goal is not proposed"
```

### HTTP の経路

```
5. POST /api/goals/<id>/content で書き換える        → 200。応答に新しい本文
6. active に投げる                                 → 409
   文言: goal 36bcae53-... is active, not proposed  ← 実際の status が入っている
7. 拒まれたあと active の本文                        → 変わっていない
8. 空白だけの content                              → 400
```

**6 が重要である。**「proposed でない」だけだと、呼び出し側は待てばよいのか諦めるのかが
分からない。`handleWithdraw` が同じ形を先に持っていたので、それに合わせた。

### 残るのは画面と、稼働版での確認

画面（`007c3e78`）は `web/src/components/GoalDetail.tsx` を触るので、
**`9f0af794`（派生元の画面）と同じファイルを触る。**同時に走らせると取り込みで衝突するので、
順に流す。**atct のファイル衝突検査は 1 セッション運用では働かない**ので、
commander が自分で順序を守る（`2026-08-22-three-tier-orchestration.md` の該当節を見よ）。

## 稼働版で書き換えを実測した（2026-08-22・0.42.0）

タスク `e89d0d00`。**このゴールが立った原因そのものを、稼働版で直した。**

対象は `44433505`。提案中のまま、本文に「フックが `herdr agent start` を見て止める」
という**2 回訂正が入った記述**が 2 箇所残っていた。

```
測定前   status=proposed  content=1507 文字  古い記述 2 箇所
         完了報告 7 フィールド すべて 0 文字

POST /api/goals/44433505.../content   → 200

測定後   status=proposed  content=1509 文字  古い記述 1 箇所（1 つを直した）
         完了報告 7 フィールド すべて 0 文字（壊れていない）

active のゴールへ同じ POST      → 409
         "goal 1dc54896-... is active, not proposed"
```

**上で書いたとおり、「完了報告が壊れないこと」は稼働版では自明にしか測れない。**
提案中のゴールは承認の決定を持つので完了報告を書けず、7 フィールドは元から空である。
非自明な形はテストのフィクスチャにある
（`TestUpdateGoalContentPreservesCompletionReport`）。

**もう半分の「履歴が残ること」は、対象そのものが無い。**人間が「提案中だけ書き換えられる」
を選んだ時点で履歴を作らないことになった。

したがってこのタスクで測れたのは 3 つである。**本文が実際に変わること・承認済みが
拒まれること・完了報告が空のまま保たれること。**3 つとも期待どおりだった。

### ここでも計測器を疑うことになった（今日 8 回目）

**最初「本文編集が配信物に無い」と読んだ。**`index.html` が読む JS 3 つを見て、
どれにも `/content` が無かったためである。

**誤りだった。**`GoalDetail` は `StateMessage` を import しており、
`api.ts` の関数はその共有チャンクに束ねられていた。

```
GoalDetail.BjCNVgry.js
  → from"./StateMessage.BfYcQvM0.js"   ← ここに /content がある
```

**`index.html` は入口だけを列挙する。**依存は module graph で解決される。
**入口の一覧を「読み込む全部」と読み替えた**のが誤りだった。

形は今日の他の 7 回と同じである。**期待に反する結果が出たとき、対象ではなく計測器が
誤っていた。**バンドルを検査するなら、`import` を辿ってから数える。
