# ゴールの本文を直せるようにする

2026-08-22。ゴール `141d71dc`「ゴールの本文を作成後に直せないので、前提が古くなった
まま承認を待たせてしまう」の中の判断。

## 起きたこと

commander がゴール `44433505` を立て、本文に「dotfiles のフックが `herdr agent start`
を見て止める」と書いた。**その後 2 回訂正が入った。**

```
1 回目  agent start には cwd の指定が無い     → pane split を見る
2 回目  subcommander は pane ではなく space   → workspace create を見る
```

**spec は 2 回とも直したが、ゴールの本文は直せなかった。**人間が承認の画面で読むのは
本文なので、**古い前提のまま判断を求めることになった。**

## 判断: 提案中だけ書き換えられるようにする。履歴は持たない

**人間の判断（2026-08-22）**:

> であれば承認後は本文変更できないけど提案中のものは変更できるだけでいいんじゃない？

```
提案中  → 書き換えられる（承認前なので、人間はまだ何も約束していない）
承認後  → 書き換えられない（承認したものが動く）
```

**これで履歴の問題そのものが消える。**

### commander の案は却下された

commander は「書き換えられるようにして、承認時の本文を決定に保存する」と提案した。
**人間はより単純な形を選んだ。**

**書き換えられる範囲を絞れば、守る仕組みが要らない。**「書き換えられるようにして履歴で
守る」は、**足す方向の解**だった。

そして**今日の実際の困り方に十分である。**`44433505` の本文を直したかったのは
**提案中の間**だった（承認を待たせている最中に前提が 2 回変わった）。

### 却下された案（記録）

| 案 | なぜ却下されたか |
|---|---|
| 別テーブルに履歴を積む | テーブルが増える。読む人がいない履歴が溜まる |
| 追記だけを許す | 誤りを直す用途に使えない |
| 承認時の本文を決定に保存 | **仕組みを足さずに済む形があった** |

## 実装の注意

- **完了報告の 6 フィールド（`work_done` ほか）は `goals` テーブルに同居している。**
  本文を更新する経路が、それらを巻き込まないこと
- `goals` を作り直す移行（`0007`）が既にある。**列を足すなら `ALTER TABLE ADD COLUMN`
  にして作り直さない**（作り直すと外部キーの問題に当たる。`1980f14` が接続単位で
  `foreign_keys` を切る処理を入れている）
- **承認済みのゴールは拒む。**`status` を見て、`proposed` 以外なら拒否する。
  エラーは `errors.Is` で区別できる形にする
- **履歴は持たない。**別テーブルも決定への保存も要らない
