# 止まらないための仕組みが、なぜ止まるのを許したか

日付: 2026-08-20
ゴール: 止まらないための仕組みが機能していない。なぜ動かないかを洗い出して直す

## 何が起きたか

commander が**人間の承認待ちを理由に全体を止めた。** そのとき**未着手のタスクは 21 件**
あった。止めた回数は 1 日で 5 回以上（リリース待ち・`chezmoi apply` 待ち・
コミット分担の確認待ち）。

**仕組みは 3 つある。** どれも止めなかった。

| 仕組み | 何をするか |
|---|---|
| Stop フック | セッションが終わろうとすると `atct pending` の全文で `block` を返す |
| 検知条件 1〜10 | 未適用の回答・開いたロック・放置ロック・未宣言のゴール・未着手のタスク・全 done・全 dropped・ロックのない doing |
| SSE の watch | 回答と wakeup をターンの途中に届ける |

## 測ったこと

### フックの内容は正しい

```
0.25.0 の出力: 2 節 2204 文字（Unfinished claimed tasks / Unstarted tasks）
0.26.0 の出力: 3 節 2550 文字（Unfinished tasks with work locks 5 件 /
                              Unstarted tasks 21 件 / Goals with all tasks done 1 件）
```

**どちらも「未着手のタスク」を含む。** フックは `pending` の全文を `reason` に入れている。

### 受け取った文面には「Unstarted tasks」が一度も無い

同日受け取った Stop フィードバックは、**すべて 1〜2 節だけ**だった。
`Unfinished claimed tasks` と `Undeclared active goals` のみで、
**21 件の未着手タスクが載った節は一度も届いていない。**

**この食い違いは未解決である。** 検証のため、フックが出した全文を
`/private/tmp/atct-fire/hook-emitted.txt` に控えて、次に届く文面と突き合わせる。
**推測で結論を書かない。**

## 根本原因（測って特定した）

**受け取っていた文面は 0.23.0 / 0.24.0 の出力と完全に一致する。**

| 版 | フックが出すもの |
|---|---|
| 0.23.0 / 0.24.0 | **522 文字・1 節**（`Unfinished claimed tasks:` のみ） |
| 0.25.0 | 2286 文字・2 節（`Unstarted tasks:` を含む） |
| 0.26.0 | 2550 文字・3 節 |

**受け取ったのは 522 文字・1 節だった。** 2 版以上前である。

理由は 3 行で説明できる。

```
hooks/stop           ->  $HOOK_DIR/../bin/atct     自分の版のディレクトリ内のバイナリ
plugin/bin/_resolve  ->  VERSION="0.26.0"          ビルド時に焼き込み
cmd/atct/pending     ->  store.Open(dbPath)        DB を直読み。稼働 daemon の版を見ない
```

**セッションが起動時に読み込んだプラグイン版のフックが、そのセッションの間ずっと使われる。**
`${CLAUDE_PLUGIN_ROOT}` がその版を指し続ける。

### これが意味すること

**条件を足しても、足したセッションには届かない。**

同日、検知条件を 3 つ実装して 0.26.0 で出した。そのあいだ動いていたフックは
0.23/0.24 であり、**そこには「未着手のタスク」の条件（0.25.0 で追加）すら無い。**
21 件の未着手タスクは、機械の側から見て**存在しない情報**だった。

**「仕組みが機能していない」の主因はここである。** 読む側の怠慢より前に、
機械が本当に無力だった。

### 決定: フックは実行時に最新のバイナリを解決する

    いま: ATCT_BIN="$HOOK_DIR/../bin/atct"
    直す: ~/.atct/bin/atct-* を版で並べ、最新を使う（無ければ従来の相対パス）

**リリースが走っているセッションにも即座に効く。**

安全性は実測済みである。**古い CLI が新しい DB を読めている**（0.23 のフックが 0.26 の
DB を読んでいた）。逆向き（新しい CLI・新しい DB）はより安全である。

**daemon に計算させる案（`/api/pending`）は今回採らない。** フックは daemon が
落ちているときにも動く必要があり、経路が 1 つ増える。まず版の解決を直して測る。

## 内容が届いていたとしても残る欠陥 2 つ

上の食い違いとは独立に、条件そのものに欠陥がある。

### 欠陥 1: 毎ターン出る条件が行動を変えない

**commander は委譲のため常にロックを持つ。** だから毎ターンこれが出る。

> A task with a work lock held by this agent session is still open.
> If you forgot to close it, close it; **if you are still working on it, continue.**

**「作業中なら続けよ」は、状況を報告して止まっても満たせる。**
いちばん頻繁に出る信号が、いちばん行動を変えない。同日 20 回以上受け取り、
20 回とも「作業中です」で通した。

### 欠陥 2: 「人間を待っている」と「別の作業がある」が結びついていない

今日の停止は**全部この形**である。承認待ちは条件になっておらず、未着手タスクは
別の条件として出るだけで、**両者が同じ理由の中で結ばれていない。**

読む側は「承認待ちだから止まってよい」と「未着手が 21 件ある」を、別々の情報として
受け取る。**前者が後者を上書きする。**

## 決定

### 1. ロック保持の文言を、次の行動が変わる形にする

    You hold N work locks. M tasks in active goals have no work lock.
    If you are waiting on a human, take one of those instead of stopping.

**M が 0 なら後半を出さない。** 収束する。

### 2. 新しい条件を足す（条件 11）

**自分が出した既定のない決定（人間の承認待ち）があり、かつ未着手のタスクがある**とき、
その両方を 1 つの理由として出す。

    You are waiting on a human for N decisions with no default. That does not
    block the M tasks below.

**既定のある決定は対象にしない**（放っておけば進むので待ちではない）。
決定が答えられるか、未着手が 0 になれば消える。**両側で収束する。**

### 3. 並び順を変える

**未着手の作業を先に出す。** 毎ターン出る条件（ロック保持）は後ろへ回す。
読む側が最初に見るものが、いちばん行動を変えるものであるべきである。

## やらないこと

- **フックを「止めさせない」形にしない。** 承認が必要な操作は実際にある
  （push・削除・設定変更）。**それを止められなくするのは別の壊れ方である。**
- **条件を増やして解決したことにしない。** 今日 3 つ足した直後にこの停止が起きている。
  **足すのではなく、いちばん出る条件を作り直すのが本題である。**

## 検証

- 未着手のタスクがある状態を実データのコピーで作り、**新しい文言が出ること**
- **着手すると（claim すると）後半が消えること**（収束）
- 既定のない決定を出した状態で、**条件 11 が出ること**
- **既定のある決定では条件 11 が出ないこと**（否定側）
- 未着手が 0 のとき、ロック保持の文言が従来どおりであること（否定側）
- **他プロジェクトのタスクを数えないこと**（同日プロジェクト漏れを 1 件出している）
