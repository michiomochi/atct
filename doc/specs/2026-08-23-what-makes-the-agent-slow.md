# エージェントの応答が遅い理由

2026-08-23。人間の指摘「atct:atct が遅いのはなぜ？」「ms レベルのものは問題ない。それ以上に
回答に時間がかかってると思うんだけどそれはなぜ？」から。

## 結論

**遅いのは daemon ではない。ターン数である。**

1 ターンごとに、それまでの会話全体に対する推論が 1 回走る。**応答時間はコンテキスト長に
ほぼ比例し、コンテキスト長はターン数に比例する。**この session は約 230 ターンのうち
**183 が wakeup の通知**で、そのうち 159 は「待機中（変化なし）」しか返していない。

## 最初に間違えた道

commander は最初 `goal.list` の応答時間を測り、30 ms かかることと、その原因が
`normalizeWorktreePath` の `git rev-parse` 3 回であることまで突き止めた。

```
--show-toplevel        9.8 ms
--git-common-dir       9.9 ms
--git-dir              （同程度）
                     ─────────
                       約 30 ms
```

ゴール数とは無関係な固定費である（HQ 2 件で 28.7 ms、atct 37 件で 28.0 ms）。
**しかしこれは的外れだった。**人間の指摘のとおり ms は問題ではない。

**記録として残す**（直す価値はある。キャッシュか、3 回を 1 回にまとめる）が、
**遅さの原因ではない。**

**返信を短くしても減らない。鳴らさないことでしか減らない。**

## 説明できる不具合

### (1) 着手できないタスクを 3 分ごとに催促し続ける（これが最大）

183 回の wakeup はすべて同じ内容だった。

```
atct wakeup: active_goals=4 unstarted_tasks=4 waiting_answer_tasks=0
             working_tasks=0 untouched_tasks=4 waiting_answers=24
```

数えられていた 4 件は、**4 件とも本文の冒頭に「〜待ちである。それが入るまで着手できない」
と書いてある。**

```
67d16ba7  handoff の経路ができたあと、4 通りを実測する      b01a92b8 待ち（proposed）
ea7de3ff  handoff の経路ができたあと、3 つの止まり方を実測  b01a92b8 待ち（proposed）
f2368bfd  見送りの経路ができたあと、催促が止まることを実測  aeb035ff 待ち（proposed）
8b8b772e  役割ごとの上限が入ったあと、3 層を立てて実測      05f6fa0e 待ち（承認待ち）
```

**commander は 1 件も無視していない。**着手できないことを確認し、理由を報告し、待っている。
それでも 3 分ごとに同じ数字が鳴る。

**これは 40997151 とは別の形である。**40997151 は「回答待ちのタスクしか無いのに
`UnstartedTaskCount` が真になる」形で、`waiting_answer_tasks` が 1 以上のときの話である。
ここでは `waiting_answer_tasks=0` で、`untouched_tasks=4` は正真正銘の todo かつ未 claim
である。**数え方は正しい。**

**足りないのは「承認されていないゴール待ち」を表す状態である。**

### (2) snooze では解けない

`aeb035ff` の snooze は「人間が『のこしておいて』と決めたもの」を催促から外す仕組みである。
**この 4 件は人間の意思ではなく、依存関係で機械的に決まる。**snooze で消すと、
`b01a92b8` が承認された瞬間に自動で戻ってほしいのに戻らない。

### (3) task.declare が呼ぶたびに全タスクを全文で返す

8 回で 61,650 バイト、1 回平均 7,706。**宣言したのは毎回 1〜4 件なのに、応答は done を
含む全タスクの全文である。**同じゴールへ宣言を重ねるほど大きくなる。

```
f7a8661b へ 3 件宣言 →  9,421 バイト（既存 5 件 + 新 3 件）
        へ 2 件宣言 → 12,044 バイト（既存 8 件 + 新 2 件）
        へ 2 件宣言 → 13,000 バイト超
いま同じ呼び出し     → 19,235 バイト
```

サーバー側の処理は **0.4 ms** である。時間ではなく、持ち込むバイト数が問題である。

### (4) decision.ask が毎回 claimable_tasks を全文で返す

7 回で 14,575 バイト。**質問とは無関係なタスクの本文である。**同じ 3 件
（`67d16ba7` / `8b8b772e` / `f2368bfd`）が 7 回繰り返し入っている。1 件あたり
400〜900 文字の「〜待ちである」という長文が、質問のたびに複製される。

`claimable_tasks` 自体は有用である（決定を park したあと別の作業へ移るため）。
**description を落とし、id と title と goal_id だけにすればよい。**

### (5) 直しても、直したセッションは速くならない

**MCP はセッション起動時にツール定義が凍る。**本日 `goal.list` を 47,473 → 5,858 文字に
したが、この session の commander はいまも旧版を呼んでいる。`atct_goal_get` も同様に
呼べない。そのため commander は 23 回ソケットへ直接 RPC を投げることになった。

**したがって性能の改善は必ず「次のセッションから」効く。**測るときはセッションを
またぐこと。

## 決まった設計

### 決定 1: 出す内容が無いなら、何も出さない

人間の指示（2026-08-23）: 「通知するものが何もない場合は空文字を通知することで ai が
全く反応しなくてよくしてほしい」。

**この方式が実際に効くことを実測した。**Monitor に 3 行流した結果:

```
printf '\n'            → 通知なし
printf '   \n'         → 通知なし
echo "MARKER-visible"  → 届いた（この 1 件だけ）
```

**Monitor は空行と空白のみの行を抑制する。**3 行流して通知 1 件、ターンも 1 回だけ。
したがって `atct watch` が黙れば、**エージェントは 1 ターンも消費しない。**今日の 183 回は
0 回になる。フィルタは atct 側で完結し、Monitor の設定もエージェント側の運用も変えない。

#### 「出す内容が無い」の判定は、前回との差分で決める

二案あった。

```
A  着手できるタスクが 0 件なら黙る
B  前回送った内容と同じなら黙る
```

**B を採る。**理由は 3 つ。

1. **今日の 183 回はすべて同じ 1 行だった。**B だけで 183 → 1 になる
2. **A は「依存待ち」を数から外す仕組みが要る。**`blocked_on_goal_id` のような列を足すまで、
   いまの 4 件は 0 件にならない。B は列を足さずに入れられる
3. **両立する。**A は依存の仕組みが入った後に重ねればよい。B が先でも邪魔しない

**変化があったときだけ鳴る**ので、着手できる仕事が現れた瞬間の反応は遅くならない。

#### 依存で着手できないタスクを外す仕組みは、別に残す

B は騒音を止めるが、**数字そのものは嘘のままである。**`untouched_tasks=4` と出続け、
その 4 件は着手できない。人間がダッシュボードを見たときに誤解する。

したがって A も必要である。**snooze とは別の仕組みにする。**人間の意思ではなく依存で
決まるので、人間の判断を要さない。タスクが待っているゴールを明示的に持たせ
（`blocked_on_goal_id` のような列）、そのゴールが active になるまで催促の対象から外す。
**active になったら自動で戻る。**

`aeb035ff` の本文に追記済み。含めるか別ゴールに切り出すかは着手する者が決めてよい。

### 決定 2: MCP の応答は、その呼び出しが作ったものだけを返す

- `task.declare` → その呼び出しで宣言したタスクだけ
- `decision.ask` の `claimable_tasks` → id / title / goal_id のみ

**返さなくなったものは `goal.get` で読める**（0.45.0 で確認済み）。
ゴール `c8b3788a` にした。

### 決定 3: 応答バイト数は変更前後で測って報告する

「小さくなったはず」では受け取らない。測り方はこの spec の「実測」の節と同じ、
transcript の解析でよい。

## 却下した案

**「待機中」の返信を短くする** — 1 ターンの固定費は中身と無関係なので効かない。実測で
20 バイトの返信が 1,342 バイトを占めていた。

**内容が無いときに空行を出す** — 出さないのと同じである。実測のとおり Monitor は空行を
抑制するので通知は飛ばないが、**わざわざ空行を書く理由が無い。**「黙る」で足りる。
ただし**空行を出しても害は無い**ので、実装が単純になるならそちらでもよい。

**wakeup の間隔を延ばす** — 着手できる仕事があるときの反応が遅くなる。間隔は
`9c7df582` で人間が 3 分と決めた数字であり、鳴る条件のほうを直すべきである。

**`goal.list` の git 呼び出しを最適化する** — 30 ms は遅さの原因ではない。直す価値は
あるが、この spec の主題ではない。別に記録する。

## 対処したこと（2026-08-23）

commander はこの session の watch を `TaskStop` で止めた。**184 回目の wakeup を最後に
待機ループが止まる。**daemon は動いたままで、ダッシュボードと他のセッションは影響を
受けない。

**代償**: 人間が承認や回答をしても commander に自動では届かない。人間が会話でその旨を
伝える必要がある。**恒久策は決定 1 であり、これは応急処置である。**

## 未検証

- `blocked_on_goal_id` を人間が付けるのか、タスク宣言時に commander が付けるのか。
  本文に「〜待ちである」と書く運用は既にあるので、そこから機械的に拾えるかもしれない
- 待っているゴールが取り下げられたとき（dropped）の扱い。永久に外れたままになる
- `output_style` の再添付 309,412 バイトと `total_tokens_reminder` 186,562 バイトは
  ハーネス側の挙動で、atct からも commander からも制御できない。**合計 13% を占めるので、
  減らせる余地があるかは別途確かめる価値がある**
