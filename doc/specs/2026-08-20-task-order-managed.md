# タスクの順番を管理できるようにする

日付: 2026-08-20
ゴール: タスクは順番で管理するようにし、一覧ではその通りに並ぶようにしてほしい

## 解く問題

**順番は既に存在し、正しい順で並んでもいる。足りないのは「見えること」と
「テストで固定されていること」である。** 実物を確認した結果:

| 現状 | 場所 |
|---|---|
| `sort_order INTEGER NOT NULL` がある | `tasks` テーブル |
| 宣言時に配列の添字で決まる | `DeclareTasks` |
| クエリは `ORDER BY sort_order` で返す | `internal/store/queries/task.sql:15, 49, 66` |
| ゴール詳細の一覧は client 側でも `order` で並べ直す | `web/src/components/TaskTable.tsx:120` |
| **ダッシュボードの木は並べ替えていない** | `web/src/components/GoalTable.tsx:54`（`tasks.map`） |
| **順番の値が出ているのはモーダルだけ** | `web/src/components/TaskDetailModal.tsx:71-72` |
| **順番を変える経路が無い** | HTTP API・MCP のどちらにも存在しない |

つまり **画面から順番を知る手段がほぼ無い。** 一度宣言したら順番は変えられないが、
**人間はそれを問題としていない**（2026-08-20 の回答: 「入れ替え機能は不要。
順番が把握できるだけでよい」）。変更の経路は作らない。

ダッシュボードの木がサーバの返す順に依存しているのは、今は正しく動いているが
**テストで固定されていない。** サーバ側の `ORDER BY` を誰かが外したら黙って崩れる。

## 決定

### 訂正（同日）: 画面に出すのは保存値ではなく位置

当初「画面に出す番号が `sort_order` そのもので、表示位置と保存された値が食い違わない」と
決めた。**その根拠は「並べ替えのときに 0 から詰め直すから」であり、
並べ替えを作らないと決めた時点で根拠が消えていた。**

さらに v0.22.0 をリリースしてから、`sort_order` が**ゴール内で一意でない**ことが分かった。
`internal/store/task.go:115` が `SortOrder: int64(i)`（バッチ内の添字）を代入するため、
同じゴールに 2 回宣言すると 0 から振り直される。実データで**重複しているゴールが 9 件**あり、
画面には `1 1 1 1 1 1 2 3 4 5 6` と出た。

**spec に「宣言時に配列の添字で決まる」と書いたが、複数バッチで衝突することを
確かめていなかった。** 順番を出す機能の設計で、順番の値が一意かを見ていない。

したがって画面に出すのは**並べ替えた後の位置（1..n）**とする。保存値の重複が画面に出ない。
保存側の衝突は別に直す（`MAX(sort_order)` の続きから振る）。

### 一覧に順番を出す

ゴール詳細のタスク一覧に、先頭列として順番を出す（1 始まりで表示する。
`sort_order` は 0 始まりなので +1 する。**人間に 0 番を見せない**）。

ダッシュボードの木には出さない。**あちらは既に `├─` で順序を表現しており、
番号を足すと 1 行に情報が 2 つ増えて密度が落ちる**（`product-ui` の密度の指針）。

### client 側の並べ替えを両方に入れる

`GoalTable` にも `sort_order` での並べ替えを入れる。サーバが正しい順で返していても、
**「サーバがそう返すから」という暗黙の依存を残さない。** 2 箇所とも並べ、
両方をテストで固定する。

### 変えないもの

- `sort_order` の列名と型
- `DeclareTasks` が添字で順番を決める挙動
- `ORDER BY sort_order` のクエリ（消さない。client 側の並べ替えは二重の保険）
- `atct_task_update` の引数（`status` のみ。順番は別の経路にする）

## 検証

- ゴール詳細のタスク一覧に順番の列が出て、**1 始まり**であること（0 が出ない）
- **入力の順序を `sort_order` の昇順と食い違わせても、画面が昇順で並ぶこと**
  （client 側の並べ替えが実際に効いているかを見る。サーバ順に依存していないことの検査）
- **ダッシュボードの木も同じ条件で昇順に並ぶこと**（今テストが無い側）
- API 変更が不要であること（`api.ts` の `TaskView` には `order` が既にある）

フィクスチャはタスク 3 件以上にし、**入力を意図的に昇順でない順序で渡す。**
既に昇順の入力を渡すと、並べ替えをしない実装でも通る。

実 HOME（`~/.atct`）の daemon は止めない。

## やらないこと

- **順番を変える機能を作らない**（人間が 2026-08-20 に「入れ替え機能は不要。順番が
  把握できるだけでよい」と回答）。HTTP API も MCP ツールも足さない
- ドラッグ＆ドロップも上下ボタンも作らない
- ダッシュボードの木に番号を出す

### 決着規則は `created_at` を先にする（同日、実データで測って変更）

当初 `ORDER BY sort_order, created_at, id` を指定したが、**実データに当てたら
既存 9 ゴールでバッチが交互に並んだ。** 先頭 5 行が 5 つの異なる宣言バッチから 1 件ずつ、
という状態になる。決定的ではあるが人間には読めない。

`ORDER BY created_at, sort_order, id` にすると、バッチごとにまとまり、
バッチが宣言時刻順、バッチ内が順番どおりに並ぶ（実測: 6 件 → 1 件 → 1 件 → 2 件 → 1 件）。
`created_at` は `2026-08-17T14:04:43Z` 形式でゼロ埋めなので文字列比較で正しく並ぶ。

**修正後の新しいデータでは、どちらの順序でも結果が同じ**（`MAX` の続きから振るので
`sort_order` も `created_at` も単調増加する）。違いが出るのは既存 9 ゴールだけである。

代償: `sort_order` という名前の列が並びの第 1 キーでなくなる。**並べ替え機能を作らないと
決めているので今は問題にならないが、将来作るなら見直しが必要である。**

## 訂正その 3（同日）: `(goal_id, sort_order)` を UNIQUE にする

人間の提案「goal_id と order をユニークにしたいけどどう？」を採用する（同日、承認済み）。

**これで上の「決着規則は `created_at` を先にする」という決定は破棄する。** 保存値が
ゴール内で一意になれば、`sort_order` だけで決定的かつ意味のある並びになり、
列名と実態が一致する。

### なぜ私の設計より良いか

Go 側の `MAX+1+i` を守らせる仕組みが無かった。**別の宣言経路が増えたら黙って衝突する。**
UNIQUE ならその瞬間に落ちる。

さらに、私が積み上げていた複雑さが丸ごと消える — `created_at` 第 1 キーの決着規則、
それに合わせるクライアント側の比較鍵の変更、「バッチが交互に並ぶ」問題そのもの。

### 「既存の値は書き換えない」を撤回する

**根拠が成り立っていなかった。** 説明の backfill との類推で決めていたが、両者は違う。

| | 書き換えの中身 |
|---|---|
| 説明の backfill | **内容を捏造する。** 実際の意図と推測が区別できなくなる |
| `sort_order` の振り直し | **既存データから位置を再計算するだけ。** 何も捏造しない |

**失う情報も無い。** バッチ内の添字は `declare_key`（`<key>#<index>` の形）に残る。

### 承知している代償

**0.21.x 以前のバイナリは、タスクが既にあるゴールへの宣言が UNIQUE 違反で落ちる**
（`SortOrder: int64(i)` を代入するため）。読み取りは通る。

このプロジェクトは「新しい DB を旧バイナリで開いても壊さない」を守ってきた
（atlas の baseline を v6 に据え置いたのはそのため）。**今回はその方針を一部破る。**
人間の承認を得ている。

### 同時宣言は接続数 1 で直列化されている

`internal/store/store.go` に `db.SetMaxOpenConns(1)` があり、コメントに
「The daemon is the single writer」と書かれている。接続が 1 本なので 2 つ目の
`BeginTx` は 1 つ目の完了まで待つ。**`MAX` 読み取りと INSERT の間に割り込みは入らない。**

断定せずテストで固定する（誰かが接続数を上げたら壊れる）。
