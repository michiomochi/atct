# タスクの順番を管理できるようにする

日付: 2026-08-20
ゴール: タスクは順番で管理するようにし、一覧ではその通りに並ぶようにしてほしい

## 解く問題

**順番は既に存在する。足りないのは「管理できること」である。** 実物を確認した結果:

| 現状 | 場所 |
|---|---|
| `sort_order INTEGER NOT NULL` がある | `tasks` テーブル |
| 宣言時に配列の添字で決まる | `DeclareTasks` |
| クエリは `ORDER BY sort_order` で返す | `internal/store/queries/task.sql:15, 49, 66` |
| ゴール詳細の一覧は client 側でも `order` で並べ直す | `web/src/components/TaskTable.tsx:120` |
| **ダッシュボードの木は並べ替えていない** | `web/src/components/GoalTable.tsx:54`（`tasks.map`） |
| **順番の値が出ているのはモーダルだけ** | `web/src/components/TaskDetailModal.tsx:71-72` |
| **順番を変える経路が無い** | HTTP API・MCP のどちらにも存在しない |

つまり **一度宣言したら順番は永久に固定**で、画面から順番を知る手段もほぼ無い。
`atct_task_update` は `status` しか受け取らない。

ダッシュボードの木がサーバの返す順に依存しているのは、今は正しく動いているが
**テストで固定されていない。** サーバ側の `ORDER BY` を誰かが外したら黙って崩れる。

## 決定

### 順番の変更は「並び全体を渡す」形にする

1 件ずつ「このタスクを 3 番にする」を受け付けると、既存の 3 番と衝突し、
呼び出し側が全体の整合を取ることになる。**ゴールに属するタスク ID の順序付き配列を
そのまま受け取り、サーバが 0 から詰め直す。**

- HTTP: `PUT /api/goals/{id}/task-order`、本文は `{"task_ids": [...]}`
- MCP: `atct_task_reorder`（`goal_id` と `task_ids`）

**受け取った配列がそのゴールのタスク全件と一致しない場合は拒否する**（欠けている・
余分がある・重複がある・他ゴールのタスクが混ざっている）。部分的な並べ替えを許すと、
渡されなかったタスクの順番をサーバが推測することになる。

### 詰め直すので `sort_order` は表示位置と一致する

並べ替えのたびに 0..n-1 で振り直す。**そうすれば画面に出す番号が `sort_order` そのもので、
「表示位置」と「保存された値」が食い違わない。** 宣言時も既にこの形になっている。

### 一覧に順番を出す

ゴール詳細のタスク一覧に、先頭列として順番を出す（1 始まりで表示する。
`sort_order` は 0 始まりなので +1 する。**人間に 0 番を見せない**）。

ダッシュボードの木には出さない。**あちらは既に `├─` で順序を表現しており、
番号を足すと 1 行に情報が 2 つ増えて密度が落ちる**（`product-ui` の密度の指針）。

### 並べ替えの操作は上下ボタンにする

ドラッグ＆ドロップは採らない。kumo に該当する部品が無く、素の HTML と CSS で
作り直すことになる（`product-ui`: 成熟した部品があるならそれを標準にする、の裏返し）。
**上下ボタンはキーボードだけで操作でき、読み上げにも乗る。**

PC 専用と決めた画面だが、それは**ドラッグを使う理由にはならない。**

### client 側の並べ替えを両方に入れる

`GoalTable` にも `sort_order` での並べ替えを入れる。サーバが正しい順で返していても、
**「サーバがそう返すから」という暗黙の依存を残さない。** 2 箇所とも並べ、
両方をテストで固定する。

### 変えないもの

- `sort_order` の列名と型
- `DeclareTasks` が添字で順番を決める挙動
- `ORDER BY sort_order` のクエリ（消さない。client 側の並べ替えは二重の保険）
- `atct_task_update` の引数（`status` のみ。順番は別の経路にする）

## 検証

- 並べ替えた後、ゴール詳細の一覧が**新しい順**で並ぶこと
- **ダッシュボードの木も新しい順で並ぶこと**（今テストが無い側）
- 並べ替え後の `sort_order` が 0..n-1 で**隙間なく**振られていること
- **否定側**: 欠けている `task_ids` を渡すと拒否されること
- **否定側**: 重複を含む `task_ids` を渡すと拒否されること
- **否定側**: 他ゴールのタスク ID を混ぜると拒否されること
- **否定側**: サーバの `ORDER BY` を外しても、client 側の並べ替えで画面の順序が保たれること
  （client 側の保険が実際に効いているかを見る）
- 一覧に出る番号が 1 始まりであること（0 が出ない）

フィクスチャはタスク 3 件以上にする。2 件では「逆順にする実装」でも並べ替えが通る。

実 HOME（`~/.atct`）の daemon は止めない。

## やらないこと

- ドラッグ＆ドロップ
- ダッシュボードの木に番号を出す
- 順番の変更を人間の操作だけに限らない（エージェントも MCP から並べ替えてよい。
  分解し直したときに順番を直せる方が自然である）
