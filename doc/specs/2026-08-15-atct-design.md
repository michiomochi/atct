# ATCT Design Specification

> The air traffic control tower for your coding agents.

- Date: 2026-08-15
- Status: Proposed (not yet implemented)
- License: AGPL-3.0, with a CLA so a hosted version remains possible
- Research basis: five documents under `doc/research/` (kept locally, not published)

**On the name.** ATCT stands for *air traffic control tower*. The metaphor is load-bearing rather
than decorative. A controller tracks many aircraft at once without flying any of them, issues a
*clearance* when an aircraft needs one, and until that clearance arrives the aircraft *holds short*:
it stops before the runway and waits, without anyone taking the controls. That is the shape of this
system. The human never operates the agents. They watch the tasks, answer the decisions, and
everything else proceeds without them.

## 1. Purpose

A human sets a goal. An AI agent decomposes it into tasks and works through them autonomously.
When a decision is needed, the agent hands it to the human and keeps going where it can. Once the
human answers, the agent resumes. When the goal is met, the agent reports back.

**The unit of management is the task, not the agent.** Agent process state (`working` / `idle` /
`blocked`) is explicitly out of scope. What a human needs to see is which tasks are in what state
and which decisions are waiting on them — not which agent is doing what.

## 2. Established facts

The design rests on five findings. Evidence lives in `doc/research/`.

1. **Task state cannot be reconstructed by observing agents.**
   Claude Code's TodoWrite exposes only `pending` / `in_progress` / `completed`; there is no status
   meaning "waiting for a human decision". Transcripts carry no stable `current_task`,
   `blocker_reason`, or `next_action` field. Codex is the same: `approval_policy` is a policy, not a
   task record. Task state therefore requires its own store that agents write to explicitly.

2. **Existing approval workflows only handle decisions defined at design time.**
   Jira Service Management approval steps satisfy every mechanical requirement — a distinct state,
   request body, named approvers, a reply path, a post-approval transition, and a REST API. But the
   approval step is configured into the workflow ahead of time. It cannot generate a new question
   with new options at runtime. Decisions arising from agent work are not enumerable in advance,
   so this gap is structural rather than incidental.

3. **No implementation delivers a decision back into a running agent session.**
   crit's "Send now" does not inject into an existing session. It spawns a fresh one-shot process via
   `exec.CommandContext`, feeds the prompt on stdin, and stores stdout as a reply
   (`server.go:3033-3092`). It tracks its own review sessions but never external agent session IDs.

4. **herdr's agent state is not semantic state.**
   Its integration sends only `pane.report_agent_session` — session identity — and hooks only
   `SessionStart`. The payload has no `state`, `blocker_reason`, `approval_request`, or
   `next_action`. Its `working` / `blocked` values are inferred from terminal titles and screen
   scraping, and cannot distinguish "working" from "waiting for approval".

5. **Demand is proven; the commercial model is what failed.**
   Vibe Kanban reached 27,800 stars and thousands of daily users, could not monetize, and is
   sunsetting into a fully local, community-maintained open source project.

## 3. Scope

### In scope

- A local database holding Goals, Tasks, and Decisions
- An MCP server that agents read from and write to
- A web UI where humans review state and answer decisions, scoped by project
- The state machine and resume mechanics that make the decision round-trip reliable

### Out of scope for v1

| Excluded | Reason |
|---|---|
| Task dependency graphs and parent/child tasks | Beads' territory. v1 carries only `order` |
| Non-human blocking (waiting on CI, etc.) | The requirement is human decisions. Mixing them pollutes the state |
| A `next_step` field per task | "What's next" is the set of `todo` tasks. Do not store it twice |
| Team sharing and multi-user sync | Local-only is a requirement. A sync layer can be added later |
| Agent lifecycle control (start/stop) | herdr's responsibility. ATCT owns tasks and decisions |
| Cost and token observability | Langfuse and AgentOps' territory |

## 4. Data model

```
Project
  └ Goal (set by the human)
      └ Task (declared by the agent)
          └ Decision (generated by the agent at runtime, answered by the human)
```

A Decision belongs to a Goal. Its link to a Task is optional, because some decisions concern the
goal as a whole.

### Project

| Column | Type | Notes |
|---|---|---|
| `id` | text | Primary key |
| `name` | text | Unique display name |
| `root_path` | text | Unique. Used to derive the project from a working directory |
| `created_at` | timestamp | |

### Goal

| Column | Type | Notes |
|---|---|---|
| `id` | text | Primary key |
| `project_id` | text | |
| `title` | text | |
| `description` | text | Written by the human. Includes the completion criteria |
| `status` | text | `active` / `done` / `dropped` |
| `result_summary` | text | Written by the agent via `goal_complete` |
| `created_at` / `updated_at` | timestamp | |

### Task

| Column | Type | Notes |
|---|---|---|
| `id` | text | Primary key |
| `goal_id` | text | |

### Decision

| Column | Type | Notes |
|---|---|---|
| `id` | text | Primary key |

| `options` | json | `[{label, description, consequence}]`. May be empty for free-form answers |
| `status` | text | `open` / `answered` / `applied` / `withdrawn` |
| `answer_label` | text? | Label of the chosen option |
| `answer_text` | text? | Free-form answer |
| `answered_by` | text? | |

`options[].consequence` states what happens if that option is chosen. It exists so the human can
decide without asking a follow-up question, and it is the concrete difference from approval
workflows that only offer approve/reject.

## 5. State machine and invariants

### Waiting is derived, never stored

Task has no `waiting_decision` status. Goal has no `review` status. Waiting is derived from the
presence of an open Decision.

| Derived state | Definition |
|---|---|
| Task is waiting on a human | The task has a Decision with `status = open` |
| Goal is awaiting completion approval | The goal has a Decision with `kind = completion` and `status = open` |

Storing the same fact twice guarantees drift: status says waiting but no decision exists, or a
decision is open while status still reads `doing`. This is exactly how file-based tracking fails,
and moving to a database does not help if the state is still duplicated. Deriving it makes the
inconsistency unrepresentable.

### Decision has three live states

```
open ──(human answers)──> answered ──(agent applies)──> applied
  └──(agent withdraws)──> withdrawn
```

`answered` is not the end. **A human having answered and an agent having received that answer are
two different facts.** If the session dies and the answer is left hanging, the decision stays
`answered` and never reaches `applied`, which makes the problem detectable. This is the structural
fix for the trap crit fell into by treating "zero unresolved comments" as approval.

The human's inbox clears at `answered`. The system tracks through to `applied`.

### Task claiming

Multiple agents may work the same goal concurrently. Without claiming, two agents can pick up the
same `todo` task and duplicate or clobber each other's work.

- Claiming is a conditional update: `SET claimed_by = ? WHERE id = ? AND claimed_by = ''`. Exactly
  one agent wins.
- A claim is released when the task reaches `done` or `dropped`, and when it returns to `todo`. An
  agent abandoning a task therefore releases it by setting the status back to `todo`, so no separate
  agent-facing release operation is needed.
- A human releases a stale claim from the goal detail screen, which calls
  `POST /api/tasks/{id}/release`. This is the only way a claim held by a dead run gets cleared, so
  it is part of v1 rather than a later addition.
- Claims do not expire automatically in v1. Automatic expiry needs a liveness signal, and the
  research established that no reliable cross-harness signal exists — a timeout would take tasks
  away from agents that are still working.

### Invariants

1. A Decision is answered exactly once. The `open` → `answered` transition is a single conditional
   update guarded by `WHERE status = 'open'`; answering twice from two browser tabs is an ordinary
   occurrence, not an edge case.
2. The `answered` transition records the answer, moves any related Task, and fires the resume event
   in one transaction. Splitting it drops answers.
3. When a `kind = completion` Decision is **approved**, the Goal moves to `done` and the Decision
   moves to `applied` in the same transaction, because there is no follow-up work for an agent to
   apply. When it is **rejected**, the Goal stays `active` and the Decision stays `answered` until
   the agent picks up the rejection reason.
4. `goal_complete` fails if the goal has any open Decision. This guarantees that a `done` goal never
   has open decisions beneath it.
5. `task_update` to `done` fails if the task has an open Decision. The agent must get an answer or
   withdraw the decision first.
6. Only agents move a Decision to `applied`. The sole exception is approval under invariant 3.

## 6. Process topology

```
Claude Code ─┐
Codex       ─┼─ atct-mcp (stdio shim) ─→ unix socket ─→ atct daemon ─→ SQLite
Cursor      ─┘                                                 │
                                                               └─→ web UI (HTTP + SSE)
```

- Agent-side configuration is a single line: `command: atct-mcp`. stdio is the lightest transport
  every harness supports.
- The shim is stateless and only forwards to the socket, so all writes converge on one process.
  herdr uses the same pattern (unix socket, newline-delimited JSON), which is verified working.
- The daemon is simultaneously the MCP backend, the web UI's HTTP server, and the SSE source.
- No harness-specific hooks are required. Anything that speaks MCP is supported.

### Project resolution

The project is derived from the agent's working directory by longest-prefix match against
`root_path`. Longest match wins so nested repositories stay unambiguous.

Git worktrees break naive path matching: a worktree lives outside the main repository, so the same
repository resolves to a different project or fails to resolve. Resolution therefore normalizes
first — it reads `git rev-parse --git-common-dir` and, when the working directory is a worktree,
maps it back to the main repository's path before matching. An explicit project argument always
takes precedence.

## 7. MCP contract

Agents get seven tools. Human-side actions (answering, approving) belong to the web UI and are not
exposed over MCP.

```
atct_goal_list(cwd)
  → active goals, plus decisions that were answered but not yet applied
  → this return value is how a new session recovers answers left by a dead one

atct_task_declare(goal_id, tasks[], idempotency_key)
  → registers the decomposition of a goal
  → re-running with the same idempotency_key does not create duplicates

atct_task_claim(task_id)
  → claims a task for this run. Fails if another run holds it

atct_task_update(task_id, status)
  → todo | doing | done | dropped. Releases the claim on done/dropped

atct_decision_ask(goal_id, task_id?, question, options[], wait_ms?)
  → parks a decision for the human
  → returns the answer if one arrives within wait_ms (default 30000), otherwise returns parked
  → omitting wait_ms waits 30000; passing 0 returns parked immediately without waiting

atct_decision_poll(decision_id?)
  → fetches answered decisions and moves them to applied

atct_decision_withdraw(decision_id, reason)
  → cancels a decision that is no longer needed
  → without this, stale questions pile up and the inbox stops being trustworthy

atct_goal_complete(goal_id, result_summary)
  → creates a completion Decision and waits for human approval
  → fails if any open Decision remains under the goal
```

`atct_task_declare` requires `idempotency_key`. Agents retry, and they re-issue the same
declaration after context compaction; without the key, tasks multiply.

## 8. Decision round-trip and resume

What the agent does while waiting is defined in three tiers.

| Tier | Condition | Behavior |
|---|---|---|
| 1 | The human is watching | `decision_ask(wait_ms=30000)` returns with the answer. The round-trip never breaks |
| 2 | Other work is available | On `parked`, move to a `todo` task that does not depend on this decision. The goal keeps moving |
| 3 | Nothing else to do, or a long wait | End the turn cleanly. State lives in the database and is not lost |

Whether a task depends on a pending decision is the agent's judgment; ATCT does not model
dependencies (out of scope). What ATCT guarantees is that a parked decision is never lost and
that its answer is delivered.

Recovery from tier 3 uses a pluggable actuator.

- **Default: no actuator.** The next agent run calls `atct_goal_list`, sees the unapplied answers,
  and continues from there.
- **Optional: herdr adapter.** On answer, run `herdr agent prompt <name>` to wake the pane. Enabled
  by configuration. Making it the default would create a hard herdr dependency.

`run_id` records which agent run parked the decision. If the same run returns, it continues; if the
run is gone, a new session adopts the decision. This is the acknowledgement and retry path that
crit lacks.

## 9. Web UI

| Screen | Contents |
|---|---|
| Inbox | Unanswered decisions across every project. **The primary surface.** Watching only this must be sufficient |
| Project list | Per-project counts of unanswered decisions and active goals |
| Goal list | Within a project: `active` / awaiting approval / `done` |
| Goal detail | Three columns — **now** = `doing`, **needs decision** = open Decisions, **next** = `todo`. Each task shows its claim holder and how long it has been held, with a release action |
| Decision detail | Question, options with label/description/consequence, free-form field, submit |

- Completion approvals appear in the same inbox as ordinary decisions. Splitting them into a
  separate screen means one of the two gets ignored.
- Updates are pushed over SSE. The design assumes new decisions arrive while the inbox is open.
- Answered-but-unapplied decisions get their own section. It is the only place a human can see that
  an answer is hanging.

### v1 minimum

Ship the inbox, goal detail, and the answer form in v1. Without them the only way to answer is the
`sqlite3` CLI, which makes daily use — and therefore validation of this design — impractical.

## 10. Storage

SQLite in WAL mode is the single source of truth.

| Requirement | How SQLite satisfies it |
|---|---|
| Atomic transitions | Transactions |
| Uniqueness | `UNIQUE` plus conditional updates (`WHERE status = 'open'`) |
| Cross-cutting queries | SQL |
| Local-only, zero install | Embedded. No external server |
| Crash safety | WAL |
| Change notification | Handled inside the daemon; no dependency on database features, since there is a single writer |

Files are not the source of truth. They cannot provide concurrent-write safety or atomic
transitions, and they degrade into the "last natural-language note written" failure the research
documented. A git-trackable form is provided by export instead.

## 11. Distribution and technology choices

### Backend

- **Go.** Shipping a single static binary is what makes zero-install possible. Use a pure-Go SQLite
  driver so cgo stays off.
- **MCP:** `github.com/modelcontextprotocol/go-sdk` v1.7.0 or later.

### Frontend

The frontend is built with Astro and React islands, styled with Tailwind, using Base UI components.
This mirrors the stack already in use in the money-portal project, so existing conventions carry
over.

For the local build the Astro output is static and embedded into the Go binary with `//go:embed`,
so end users need no Node runtime. The daemon serves those assets and exposes HTTP plus SSE.

This choice is made with a future hosted version in mind: the same frontend can be rebuilt against
a Cloudflare adapter with D1, Drizzle, and an auth layer, without rewriting the screens. Carrying
two separate frontends would cost more than the Node toolchain does.

The cost is real and worth stating: contributors who touch the UI need Node and pnpm. Prebuilt
assets are committed so that contributors working only on Go can build without them.

## 12. Success criteria

1. A human registers one goal; an agent decomposes it, works through it, takes at least one decision
   from the human, and reaches approved completion.
2. Killing the agent session after parking a decision loses nothing: the answer survives and the
   next session picks it up from `atct_goal_list`.
3. Two browser tabs answering the same decision simultaneously produce exactly one answer.
4. Both Claude Code and Codex can use ATCT over MCP with no harness-specific configuration.
5. A human watching only the inbox never misses a decision.
6. Two agents working the same goal never both hold the same task.

## 13. Open questions

These are settled during implementation. There is no basis for deciding them now.

1. **Whether 30 seconds is the right default for `wait_ms`.** It depends on MCP client timeouts and
   needs measurement. Too long and the harness aborts the tool call.
2. **How to get agents to follow the three-tier behavior.** Whether tool descriptions suffice or a
   skill/prompt convention is required. If descriptions suffice, one dependency disappears.
3. **How to notify a human that a decision has arrived** outside the hours the web UI is open. OS
   notifications, Slack, and email all add external dependencies, so v1 ships the inbox alone and
   waits for the gap to be demonstrated in use.
4. **Whether stale claims need automatic expiry.** v1 relies on a human releasing them. Automatic
   expiry requires a liveness signal that the research showed does not exist across harnesses.
