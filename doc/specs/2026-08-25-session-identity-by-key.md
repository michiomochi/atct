# エージェントの同一性を呼び手が持ち込む（2026-08-25 の設計）

**決定 `8487cae1` で確定した形の設計である。**先行する調査は
`doc/specs/2026-08-25-session-id-swap.md`。あちらは観測、これは決定と理由。

## 1. 問いは生存判定ではない

    claim が記録したいこと   どのエージェントが持っているか
    実際に記録しているもの   どの HTTP セッションが持っているか

`agent_sessions.id` は `internal/daemon/server.go` の `HTTPHandler` の中で daemon が
transport のセッションごとに振る UUID である。**エージェントは自分の識別子を選ばないし、
知らない。**MCP が再接続するたびに新しい行ができ、claim と handoff は古い行に取り残される。

当初 commander は「生存の指標を `last_seen_at` に変える」を推奨した。**人間の指摘で
取り下げた。**生存の指標をどれだけ精密にしても、再接続で作られた行は別人のままである。
**先に決めるべきは同一性で、生存はその後である。**

観測（2026-08-25、稼働版 0.54.0 と 0.55.0）:

    daemon が生きている   死んだセッションが生存扱い。自分の前の ID から引き継げない
    daemon を再起動      生きているセッションが全部死亡扱い。claim が一斉に落ちる

前者を 3 回、後者を 1 回踏んだ。**どちらも同じ 1 行が原因である**——`pid` に
`os.Getpid()` を入れる行が、stdio では「そのエージェント」を指し、HTTP では「daemon」を
指す。型は同じ、意味だけが変わる。コンパイルもテストも通る。

## 2. 採る形: 呼び手が鍵を持ち込む

    呼び手が安定した鍵を持ち込み、同じ鍵なら既存の行に再接続する。
    鍵の中身は呼び手の勝手で、atct は何かを知らない。

**ヘッダ経由は採らない。経路が存在しない**（実測・2026-08-25）。

    .mcp.json   type と url だけ。headers の項目が無い
    server.go   r.Header を読む箇所が 0 件

したがって鍵は**ツール呼び出しで提示する。**

## 3. 決めたこと

**鍵は `agent_sessions.session_key`。**`TEXT NOT NULL DEFAULT ''` とし、空でない値にだけ
効く部分 UNIQUE インデックスを張る。同じ表の `pid` / `started_at`（migration 0004）と
同じ形で、UNIQUE に NULL の三値論理を持ち込まずに「鍵なし」を表せる。

**提示は専用のツール 1 つ。**`atct_role` に引数を足す形は採らない。鍵の提示は他のどの
atct 呼び出しよりも先でなければならない——先に別の呼び出しをすると、これから捨てる行に
handoff や claim が記録される。`atct_role` は「確かめる」読み取りであって、同一性を
書き換える場所ではない。

**付け替えの意味。**提示された鍵を既に持つ行が呼び手の transport 行とは別に存在するとき、
その行が呼び手の同一性になる。同時にその行の `pid` と `started_at` を現在のプロセスのものに、
`registered_at` を現在時刻に更新する。**この更新が daemon 再起動からの回復そのものである。**
古い行の pid は死んだ daemon のものなので claim が死亡扱いになる。**鍵を持つ者だけが
更新できるので、他人が claim を復活させることはできない。**

**新しく作られた transport 行は消さない。**手順を破って提示より前に呼び出しをしていた場合、
その行は handoff から参照されている。消すと参照が孤立する。参照が無ければ既存の retention
掃除で期限切れになる。

**鍵を提示しない呼び手の振る舞いは変えない。**追加だけで、既定の経路を変えない。

**生存判定（`claimIsRunning`）は変えない。**同一性が直れば、生存判定は正しい行に対して
働くようになる。方式の再検討は別の問題として残す。

## 4. 鍵を atct は選ばない

鍵の中身は呼び手の勝手である。したがって `hooks/session-start` に取得経路を作らない。
`skills/atct/SKILL.md` が受け手にこう指示する——**セッションの間ずっと変わらず、自分だけを
指す鍵を最初に提示せよ。自分のエージェント名でよい。**

これはハーネスに依存しない。オーケストレーションの規約が各 pane に一意で安定した名前を
与えており、依頼書が受け手に自分の名前を伝えている。

## 5. これで直らないもの

**再接続そのものは検知できない。**エージェントは自分が別人になった瞬間を知らない。
知るのは「役割が思わぬものに戻っていた」ときである。**変わるのは回復の手順である。**

    いま        commander だけが直せる（project release → claim。再発行には project claim が要る）
    この後      本人が同じ鍵を提示し直せば元の行に戻れる

subcommander が自力で戻れないという制約（`2026-08-25-session-id-swap.md` の 7 節）は、
これで消える。

## 6. 未確定

- **鍵の衝突を誰も検査しない。**2 つの pane が同じ鍵を提示すれば、後の者が前の者の行を
  奪う。それが「同じ鍵なら同じエージェント」の意味なので設計どおりだが、
  **誤って同じ名前を付けた 2 つの pane は静かに 1 人になる。**
- **提示を忘れた呼び手は今までどおり壊れる。**互換のためにそうしているので、
  「壊れなくなった」とは言えない。
